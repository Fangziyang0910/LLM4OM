# 以 LangChain 运行时和最小核心重建平台

## 背景

v0.37 的平台自建了 LLM 网关、请求记账、预算预留、崩溃恢复与回放、调用证据哈希、阶段产物与修正链、插件契约和能力预检。接入一个新方法（例如 TriVAL）需要把它的流程翻译进这套抽象。抽象本身成为接入成本的主要来源，而这些能力大多在 LangChain 和 LangGraph 中已经存在，或者当前研究并不需要。

## 决定

平台只保留建模、求解和过程记录：

- LLM 调用使用 LangChain 聊天模型。调用记录、计数和上限通过回调实现，不再自建网关。
- 方法是一张 LangGraph 图，即使只有一个节点。状态继承 `ModelingState`（输入 `problem`，输出 `formulation`、`code`），节点通过 `Runtime[Context]` 取得 LLM、求解和运行记录。LangGraph 本身就是平台的方法抽象，平台不再定义阶段、产物或插件接口。运行步骤直接来自节点更新。
- 代码契约统一为 `build_model(data)`：代码构建模型，平台求解。（导出 MPS、后端与求解器任意组合的做法已由 [0008](0008-code-language.md) 取代：用户选择代码写法，写法决定求解器。）
- 研究方法的核心建模逻辑忠实移植：编排、提示、解析和停止条件来自上游。生成代码的提示按所选代码写法动态组装：通用提示拼接平台代码契约并替换库名；原提示逐句针对某个库时（OptiMUS、AutoFormulation 针对 gurobipy），为每种写法准备方言，gurobipy 方言就是上游原文。
- 运行记录只有 `run.json`、追加式 `events.jsonl` 和 `result.json`。不做恢复、回放、哈希证据和派生版本。（已由 [0009](0009-langgraph-server.md) 取代：运行由 LangGraph 服务器保存为线程。）

## 取舍

- 生成代码与导出、求解在同一个 Worker 进程中运行。恶意代码可以伪造求解结果。容器隔离（无网络、只读、非 root）仍然阻止它影响主机。当前用户是研究者本人，生成代码来自自己配置的 LLM，这一风险可接受。需要对外开放时，再把求解移到独立进程。
- 运行中断后不能续跑，只能重新运行。
