# LLM4OM 1.0 需求规格

文档修订：0.4.0。基线日期：2026-10-08（Asia/Tokyo）。状态：1.0 需求与设计基线；S01 离线切片已实现，完整 1.0 尚未验收。核心对象／配置／Manifest 草案为 0.2.0，GroundedLPIR 为 0.1.0。需求中的 MUST／必须为 1.0 发布要求，SHOULD／建议为有明确价值的后续或可选要求。需求来源与设计追踪见 [需求分析](analysis.md)。

## 1. 产品定义与目的

LLM4OM 是一个通用开源自动优化建模集成平台，用共同接口组织建模方法、语言模型、任务与数据、建模输出、建模语言、求解器、评估器和执行基础设施。

自动建模分为 Formulation（数学表述）和 Code（求解实现）两阶段，Solve 为随后的数值求解。Formulation 默认按集合、参数、变量、目标和约束组织；方法可以联合生成或迭代修正阶段输出。

核心用例是输入自然语言问题及可选数据，指定建模方法、LLM 与兼容求解配置，获得建模输出和求解结果。CLI 与 Web 可视化工作台是正式入口，调用同一 Python 应用接口。Benchmark 通过复用这条单问题流程进行批量实验。

平台目标是降低接入、使用与比较自动建模工作的成本：接入一个新方法应只需实现插件及其适配，不修改调度内核；更换模型、数据集或求解器应在能力允许时通过配置完成。后续算法选择、算法设计及优化分析可以复用建模与证据基础。

**通用性是契约与扩展能力；1.0 的执行保证范围是 LP/MILP。** 不能由一个通用插件接口推导出平台已可靠覆盖 NLP、MINLP、CP、随机规划或任意工程问题。

## 2. 已确认要求与设计默认值

用户明确要求：面向科研与开发者的通用开源自动优化建模集成平台；多种 benchmark、建模方法、LLM 和求解器可接入；方法、问题、建模输出与求解等按职责形成共同抽象；输入自然语言问题后，使用指定方法建模并调用求解器；提供 CLI 与 Web 可视化入口；需求说明、分析、架构及详细设计兼顾软件开发与领域科研；参考资料详细整理代表性论文、代码和链接。仓库当前保持私有，后续按文档开发。

已确认的建模与接入范围：Formulation／Code 两阶段，以 LLMOPT 五元素组织默认表述；首批优先 OptiMUS／CoE，模型以通用外部 LLM 为主，暂不集成专用训练权重；基准为 NL4Opt、NLP4LP 和 MAMO 的 LP/MILP 子集。训练类工作的流程／提示适配另作明确变体。

可调整的工程默认值：Python 应用接口／SDK；本地单用户 Web；先支持 LP/MILP；本地单机和容器执行；Apache-2.0；代码接口英文、说明文档中文。主要用户与 CLI/Web 入口已由用户确认，不再列为默认假设。详见 [决策记录](../decisions-and-open-questions.md)。

## 3. 用户与工作场景

| 用户 | 核心任务 | 成功条件 |
|---|---|---|
| 自动建模研究者 | 固定模型与预算，比较多个方法 | 实验可复现、结果可解释、分母与失败样本可核对 |
| 方法开发者 | 接入新 Agent／搜索方法 | 不改内核，通过契约测试即可被发现与调度 |
| LLM／后端开发者 | 接入新提供方、建模接口或求解器 | 能力和不兼容原因明确，核心对象无需被污染 |
| 数据与评测维护者 | 接入／清洗基准，定义独立检查器 | 不泄漏参考答案，能追踪原始 ID、清洗原因与协议版本 |
| 平台使用者 | 输入描述与数据，检查并求解模型 | 可以检查产物、补充需求、看到失败原因与证据限制 |

### U01：单个问题建模

输入自然语言及可选 CSV／JSON 数据，选择方法、模型与可兼容求解配置；平台预检后运行，输出候选模型、假设、需求映射、代码、决策解、目标值、求解状态、运行记录和验证报告。用户无需提供参考答案或手工拆分需求条目。无 oracle 时，独立检查标为不可用；失败也保留可检查产物。

### U02：公平方法比较

固定问题样本、模型配置、推理预算和评测协议，批量运行多个方法；统计成功与失败、延迟、成本可用性及证据覆盖率。输出逐样本明细，禁止只汇总成功样本。

### U03：第三方插件接入

通过独立 Python 包注册方法或后端；声明契约版本、能力、配置结构及依赖；通过预检与契约套件后，SDK／CLI／Web 均可使用该插件。

### U04：已有论文流程接入

优先接入 OptiMUS 和 CoE，固定上游提交与依赖，主要使用通用外部 LLM，保留原生代码路径；对适配行为、参数差异、预算及不支持的后端组合做明确记录。原模型、提示、表述或选择策略变化使用明确变体 ID。训练类工作的提示／流程可作为变体接入，暂不加载其专用权重；这不标为原训练模型的完整复现。

### U05：中断恢复与审阅

中断后可以读取已保存候选与预算，恢复未完成任务；人工修改问题或产物建立新的 revision／派生 run，不静默修改原实验。需要补充需求时，交互模式进入待输入，批量模式记为未解决。

## 4. 1.0 范围与发布门槛

| 维度 | 1.0 必须交付 | 后续扩展 |
|---|---|---|
| 问题类型 | LP、MILP；连续、整数、二元变量；有限数据实例 | QP、NLP、MINLP、CP、不确定性与多目标优化 |
| 方法 | `direct` 工程对照、固定版本 `optimus` 与 `coe` 流程适配器 | feedback_repair 对照、LLMOPT 等流程变体、MCTS、ORPilot |
| LLM | OpenAI-compatible 与 Anthropic 两类真实提供方接口；离线 Mock；主要使用通用外部 LLM | 专用训练模型通过共同 LLM 接口配置；Gemini、本地原生协议 |
| 数据 | 用户文本＋CSV／JSON；NL4Opt、NLP4LP 与 MAMO EasyLP／ComplexLP 中的 LP/MILP 数据适配器 | IndustryOR、OptMATH、其他领域基准；MAMO ODE 暂不接入 |
| 模型表示 | 五元素 Formulation；Grounded LP/MILP IR；Code 的 Python 工厂与可追踪原生代码 | 更丰富表达式与符号索引、外部语言 |
| 建模／求解 | Pyomo＋HiGHS；Pyomo／gurobipy＋Gurobi | CPLEX、SCIP、其他建模语言与求解器 |
| 入口 | Python SDK、CLI、本地单用户 Web 工作台 | 团队权限、托管部署、集群队列 |
| 执行 | 隔离容器、资源限制、默认无网络；明确标识受信任本地执行 | 分布式执行、远程隔离环境 |
| 评测 | 逐样本证据、目标值匹配及独立检查器接口；统计与报告 | 完整语义等价证明、自动化专家评价 |
| 实验 | 配置、预算、版本、轨迹、取消、恢复、结果复用 | 分布式多租户实验管理 |

direct、OptiMUS 和 CoE 均须在公开输入上输出可评估建模输出；论文流程的原生代码路径不要求支持 HiGHS。缺失 Formulation 的方法明确阶段不可用，不补造五元素。Gurobi 为可选依赖，但“已支持 Gurobi”的发布声明须有真实许可证环境下的验收证据。真实提供方调用与上游适配的测试不能用 Mock 冒充。

## 5. 功能需求

### 5.1 插件与配置

| ID | 优先级 | 要求与可观察验收结果 |
|---|---|---|
| FR-01 | MUST | 统一插件 Manifest，声明种类、插件 ID、版本、契约范围、能力、配置结构与依赖。错误版本在执行前拒绝并定位字段。 |
| FR-02 | MUST | 从内置注册及已安装的 entry points 发现插件；第三方插件不修改核心即可列出、预检、运行。重复 ID 不静默覆盖。 |
| FR-03 | MUST | 方法、LLM、任务、数据、编译、建模后端、求解器、评估器、执行器、产物存储、报告器有明确接口；不强迫每次运行使用全部接口。 |
| FR-04 | MUST | 能力匹配必须校验产物类型、问题类型、建模后端、求解器、LLM 功能、隔离环境和评测证据。未知／不兼容能力产生确定原因；不得隐式替换。 |
| FR-05 | MUST | 用版本化配置启动单问题／实验；方法参数与提供方参数分别校验。配置中的密钥只能使用环境变量引用或运行时秘密引用。 |
| FR-06 | MUST | `plugins list` 和 `doctor` 显示插件能力、配置错误、缺失依赖、许可证／模型连通性检查结果；连通性检查需显式启用，不能默认产生付费调用。 |

### 5.2 问题、任务与数据

| ID | 优先级 | 要求与可观察验收结果 |
|---|---|---|
| FR-07 | MUST | ProblemSpec 支持原始描述、语言、问题类型提示、需求条目、数据引用、假设与 revision；保留未经改写的来源。文本即可发起任务，requirements 可空、类型可 unknown，不能强制用户先完成结构化建模。 |
| FR-08 | MUST | TaskAdapter 把来源拆成公开 ProblemSpec 和隐藏 EvaluationOracle；运行方法无权访问 oracle、参考模型或参考目标。 |
| FR-09 | MUST | CSV／JSON 加载器校验路径、类型、键、缺失值、重复行及文件大小，给出行列级错误；生成文件校验和。不得无记录填补业务缺失数据。 |
| FR-10 | MUST | 数据集记录来源、许可、原始 ID、版本、split、内容哈希、清洗理由；相同问题的不同清洗版不得混合成一个结果。 |
| FR-11 | MUST | NL4Opt、NLP4LP、MAMO LP/MILP 子集的导入不把数据复制进核心包；支持指定本地已下载路径与显式 fetch。导入前核对实际版本和格式，不假设样本数恒定。 |
| FR-12 | MUST | 跨模块数据引用通过 ArtifactRef 与受控读取；大表格只按允许的行／列／摘要读取，并记录暴露给 LLM 的数据视图。 |

### 5.3 建模方法与模型调用

| ID | 优先级 | 要求与可观察验收结果 |
|---|---|---|
| FR-13 | MUST | 方法接口接收公开问题及受预算约束的 Context，输出候选与最终选择／待输入／失败；候选、调用和父子关系可追踪。 |
| FR-14 | MUST | `direct`、`optimus`、`coe` 的 Formulation／Code 行为、候选选择、修正次数和上游来源被记录；通用外部 LLM 与原模型条件的差异可查。训练类工作的流程适配使用明确变体 ID，不宣称复现未接入权重。 |
| FR-15 | MUST | LLMProvider 统一消息、结构化输出请求、工具请求、响应、使用量和错误；不支持的功能预检失败或使用显式标记的变体。 |
| FR-16 | MUST | OpenAI-compatible 可配置端点与模型，包括支持该协议的本地部署；Anthropic 使用独立适配器。远程调用包含超时、取消、限流与有界重试。 |
| FR-17 | MUST | 统一预算限制 LLM 调用／token、候选、修正轮数、求解次数、墙钟时间与并发；实际重试计入资源消耗，不通过重试绕过预算。 |
| FR-18 | MUST | 支持固定模型与预算的方法比较和按角色配置模型；报告中将同模型比较与异构模型组合比较区分。 |
| FR-19 | MUST | 方法可以提出结构化澄清请求；交互暂停后可恢复。批量无交互时以 `unresolved` 记录，不用 oracle 或 LLM 臆测补齐后仍声称原题已解决。 |

### 5.4 建模输出、编译与求解

| ID | 优先级 | 要求与可观察验收结果 |
|---|---|---|
| FR-20 | MUST | 每个 Candidate 包含共同封装及独立 Formulation／Code 引用、阶段可用性、假设、数据绑定、需求映射、警告与生成来源。默认 Formulation 使用五元素；自由文本与可编译严格 IR 分别标识。区分参数化表述与具体实例、原始表示与推断视图；保存可获得的参数／索引来源，缺失明确标记，不能虚构数学模型说明。 |
| FR-21 | MUST | IR 采用版本化 LP/MILP 结构，变量域、边界、线性目标、约束、常数与来源明确；非法变量引用／非有限值／非线性结构执行前拒绝。 |
| FR-22 | MUST | IR→Pyomo 编译是确定性转换，单独验收语义保持；不依赖 LLM 二次改写。Code 可由方法生成或严格 IR 确定性编译得到，均记录来源与表述引用。原生代码可直接走对应 Backend，不要求可靠提取完整 IR。 |
| FR-23 | MUST | 工厂代码采用明确入口构建模型；原生代码适配声明支持组合与结果抽取能力。平台不把 gurobipy 自动宣称为可切换到 HiGHS。 |
| FR-24 | MUST | SolverBackend 标准化原始状态、可行解、目标值、best bound、gap、耗时和终止原因；time limit 下有解与无解不同，infeasible 与 unbounded 不合并。 |
| FR-25 | MUST | Pyomo＋HiGHS 与 Gurobi 路径通过真实微型 LP／MILP 验证；缺少可选求解器不阻止其他组合使用，不能伪造已运行结果。 |
| FR-26 | MUST | 保存模型、代码、编译映射、求解日志、归一化结果与数据哈希；人工作出的修改形成新 revision／派生运行并记录父记录。 |

### 5.5 执行、评估与实验

| ID | 优先级 | 要求与可观察验收结果 |
|---|---|---|
| FR-27 | MUST | 生成代码默认在无网络容器执行，无 LLM 密钥、oracle 或宿主写入权限；限制时间、CPU、内存与输出，停止时清理子进程。 |
| FR-28 | MUST | 基准评估在建模完成之后由独立 Evaluator 执行，公开反馈与隐藏评分分开；相同原始答案不得在修正提示中泄漏。 |
| FR-29 | MUST | 分别输出 Formulation 检查、Code 检查、执行、候选模型可行性、独立可行性、目标值匹配与语义证据；无对应 oracle 的检查标记 `not_available`。 |
| FR-30 | MUST | 对所有已纳入评测样本输出结果，明确分母、失败类型、排除原因与统计协议；费用未知不得填写零。 |
| FR-31 | MUST | 配置实验矩阵：任务／方法／模型／后端／重复次数／预算；不支持的组合预检报告并要求明确的排除配置。 |
| FR-32 | MUST | 运行轨迹记录插件与契约版本、方法论文／变体标识、代码／提示／数据哈希、模型标识、随机种子、调用、候选、阶段输出和评估；阶段联合调用不重复计费，往返修正可追踪；能够区分回放记录与重新调用模型。同名 benchmark 按来源与版本区分。 |
| FR-33 | MUST | 运行可取消、失败隔离、检查点恢复。已完成外部调用的响应已持久化时不得重复发起；未知结果的调用在恢复时明确标记可能重复与预算处理。 |
| FR-34 | MUST | 导出 JSONL／CSV 逐样本结果和 Markdown／HTML 报告；包含能力覆盖、运行失败、证据级别、预算、时间和成本可用性。 |
| FR-35 | MUST | CLI 与本地 Web 工作台可提交问题、配置兼容组合、查看运行／候选／建模输出／决策解及批量结果、取消／恢复；调用同一 Python 应用接口，不另实现建模或评估逻辑。 |
| FR-36 | MUST | 提供离线 Mock 和自建微型任务、插件契约套件及完整流程示例；Mock 输出有标识，不进入真实方法准确率排名。 |

### 5.6 1.0 之外

1.0 不承诺完全自动理解含糊业务需求、不承诺证明任意自然语言与模型等价、不开发新数值求解器、不训练新基础模型、不自动设计启发式算法、不搭建公共排行榜或多租户 SaaS。不改变问题类型标签来掩盖不支持的问题。预留接口是后续工作入口，不是已交付功能。

## 6. 非功能需求

| ID | 要求 | 验收口径 |
|---|---|---|
| NFR-01 | 可扩展 | 新增独立方法／Provider／任务／求解器不修改调度内核；至少一个第三方方法包在独立安装环境演示。 |
| NFR-02 | 可复现 | 固定输入、Mock、IR 编译与求解 fixture 可以重复得到同一结构及容差内结果；真实 LLM 不承诺 bitwise 确定性。 |
| NFR-03 | 可观测 | 每个阶段都有结构化事件、关联 ID、阶段耗时和错误；报告能定位一次失败到具体候选与依赖。 |
| NFR-04 | 隔离 | 容器模式阻止 fixture 中的越界文件读写与网络访问，OOM／timeout 不使调度器退出；明确列出测试的威胁范围。 |
| NFR-05 | 性能 | 在记录配置的 Linux 4 vCPU／8 GiB、并发 4 的参考环境，1,000 个离线短任务无任务丢失；相对直接执行相同任务的调度附加时间 P95 ≤ 500 ms。LLM、容器首次启动和求解耗时分别统计。 |
| NFR-06 | 稳定性 | 100 个任务批次含异常、限流、超时、取消及恢复，其他任务正常完成，终态／预算／产物无重复或错配。 |
| NFR-07 | 可移植 | 核心与 CLI 支持 Python 3.11／3.12；Linux 为完整隔离验收环境，macOS 支持容器客户端和本地受信任模式；Windows 初期 best effort，不能标成已验收。 |
| NFR-08 | 依赖可控 | 可选集成依赖按需安装；安装核心与 HiGHS 路径不要求商业许可证或所有厂商 SDK。Messages 当前使用标准库 HTTP，无 Anthropic SDK 依赖。 |
| NFR-09 | 可理解 | 中文主文档、英文接口；报告明确执行模式、证据限制和失败原因；密钥不进入配置导出、日志或异常。 |
| NFR-10 | 版本声明与校验 | Manifest、核心数据对象、IR、事件与评测协议分别版本化；读入不支持的版本 fail fast；指标口径由协议版本固定。当前设计以最新草案为准。 |
| NFR-11 | 可维护 | 契约套件、确定性 fixture、集成测试与真实外部测试分层；外部不可用报告 skip／原因，不能抹除失败。 |
| NFR-12 | 开源准备 | 记录第三方来源、上游提交、许可与数据使用范围；正式引入代码前完成许可证兼容检查，不能从论文表格推断可复制权利。 |

NFR-05 是工程验收目标，尚未测量。首次开发应建立测量基线；改动目标必须同步修改规格与决策记录。

## 7. 产品输出与入口

最低输出是一份 RunBundle：公开输入快照、脱敏配置、版本锁定、每个候选产物、调用与预算轨迹、编译与求解信息、原决策映射、可获得的独立评估证据和最终报告。失败、取消或待输入同样能生成不完整但有效的 RunBundle。单问题用例不要求存在 benchmark 或 oracle。

Web 1.0 包含：插件与环境页面、单问题运行页面、候选与产物页面、实验配置／进度页面、逐样本结果与比较页面。允许导入／下载 JSON 与表格，不以聊天界面替代结构化结果。

## 8. 成功指标与发布验收

平台成功首先以工程能力衡量：第三方插件无需修改内核；三种方法可统一运行；至少两类真实提供方适配；两个真实求解器路径；NL4Opt、NLP4LP、MAMO LP/MILP 三个基准适配；离线端到端与独立评测可复现；CLI／SDK／Web 共用核心；失败和恢复有完整记录。

模型准确率不预设 90% 等任意发布门槛。首次实验比较 direct、OptiMUS、CoE 在相同通用 LLM 下的流程，给出真实 baseline、逐样本证据、预算与错误分析，后续方法改进再与固定基线比较。没有真实凭据的适配器可合并为未验收功能，但 1.0 宣称完整支持前必须补齐真实验收证据。

详细验收场景见 [验收清单](../acceptance.md)，实现顺序见 [开发计划](../implementation-plan.md)。当前仓库交付需求与设计基线，平台实现状态由切片验收记录确定。
