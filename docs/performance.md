# 工作台性能与容量

这次优化集中在首页启动、历史刷新、对话附件和求解结果读取。四个并发的生产计划算例均由 Docker 中的 HiGHS 求得最优值 13，A 为 3、B 为 2。平台节省的资源主要来自减少重复传输、持久化和渲染。

## 同机测量

2026-11-23 在同一台 i9-14900KF、Linux、Python 3.12.11 主机上对比提交 `ac10adb` 与优化后的工作树。两版使用相同依赖、生产构建、求解镜像和独立测试工作区。模型端使用固定回复的本地服务，用于让两版生成相同的模型。MB、KB 按十进制计算，进程内存使用 MiB。

**浏览器。** 在 1440 × 900 的 Chromium 窗口中分别新建五个浏览器上下文，每个上下文各测首次和再次打开。用 DOM 观察器记录输入框首次出现的时间，以 Resource Timing 的 `transferSize` 统计同源静态资源。两版再次打开时静态资源传输都为零。历史包含 16 个尚未启动的草稿，首次打开两版各核实 16 次。后续仍每 10 秒刷新空闲历史，有活动运行时为 4 秒。未订阅的草稿状态缓存按当前客户端默认设置在 5 分钟后回收，届时会重新核实。

**结果与对话。** 固定方案包含 7,680 个变量和 180,000 B 的 CSV。第一次打开变量表后，两版均显示相同的 4,800 个单元格。另起一个空工作区，通过真实对话页面上传 200,011 B 的 CSV 并连续对话五轮。统计第二轮发送至回复结束并完成刷新之间的 API 请求与响应正文，包括流式事件。优化版其中 1,119,507 B 来自原生事件流，主要成本仍是随检查点传输的附件。退出服务后计量全部原生 `.pckl` 文件，重启后逐项核对完整 CSV 和十条消息。

**服务与求解。** 选项目录用 16 个客户端并发发出 160 次请求，表中为三轮各自 P95 和进程 CPU 时间的中位数。另用 12 个客户端各发出 8 次目录、静态资源、历史和检查点读取请求，同时经 API 发起 4 个 Direct / Pyomo / HiGHS 求解。两版各 96 次读取及 4 个求解均成功。在同一机器上交替两次启动各版本，重放这一混合负载，每 20 ms 采样服务进程 RSS。表内范围为两次观测的峰值，沙箱容器和浏览器另计。10 万变量测试用 `tracemalloc` 单独测量一次结果查询的额外分配。

## 开销从哪里减少

| 路径 | 实现 |
|---|---|
| 首次访问与重访 | 输入区先加载，手动编辑器、消息、建模面板和图表按需加载。大于约 1 KB 的脚本和样式随包附 gzip 版本，构建产物多占 733 KB。服务按请求选取预压缩文件，浏览器缓存按内容哈希区分版本。 |
| 标题、状态和历史 | 侧栏可见时才查询。按线程更新时间复用已确认的空闲草稿状态，活动线程继续核实。查看固定方案时只读元数据和指定检查点，切走时取消尚未完成的请求。 |
| 连续追问与数据编辑 | 首次提交或实际编辑时保存附件。后续只提交新消息，从检查点恢复题面与数据。每次发送附带当前页面所见输入的 SHA-256 指纹。执行前发现其他窗口已修改时，提示核对并停止该轮模型调用。页面重新打开且有待确认消息时读取完整线程快照。 |
| 大结果与流式步骤 | 有业务解读时延迟创建明细表，首次打开后保留筛选状态。纯文本增量沿用现有步骤列表。后端按变量名直接读取，翻页只保留本页，表达式引用整组数值时才构造所需数列。 |
| 选项、后端探测与翻译 | 每个服务进程只生成一次公开选项目录。用户指定建模库或实际需要校验时才获取后端目录。已缓存译文可直接读取，重复的翻译请求仍共用一次模型调用。 |

## 部署与下一处瓶颈

完整运行和沙箱各有独立名额，默认都为 4。单个 Docker 求解容器的上限为 2 CPU、2 GiB，四个同时求解的容器合计最多 8 CPU、8 GiB，另需预留服务和操作系统的内存。外部模型响应慢时，运行占着名额，沙箱可能空闲。根据代表性模型的实际内存、排队等待和限时完成率选择两个并发数。配置和只启动工作台的命令见[部署指南](deployment.md#并发)。

在优化版重放同一组小整数规划时，通过 cgroup v2 确认四个求解容器同时存活，单容器内存峰值为 44.9–52.6 MiB。同步采样得到四个容器合计最高约 166 MiB。这给出的是该模型的实际开销。更换模型规模或求解器后应重新测量。

长期工作区的容量主要受内存运行时约束。当前锁定的 `langgraph-runtime-inmem 0.36.4` 每 10 秒序列化已登记的非空存储。在有历史而无新请求的隔离工作区，观察到同一份 346,138 B 的原生存储文件在 11.5 秒观测窗口内被重新写入。历史持续增加时，应在真实工作区记录快照大小、磁盘写入量、服务 RSS 和查询延迟。如果历史成为主要开销，下一步是用代表性历史验证增量持久化后端及重启恢复，再做迁移。当前部署按一个工作区一个服务进程运行。

特别大的单个方案还有一项可测的成本。固定方案页仍需取得用于历史复现和导出的完整检查点，7,680 个变量的样本在线程接口上仍读取约 320 KB。如果生产中的大方案主要用于浏览摘要，可进一步按检查点 ID 提供摘要和分页变量，在展开、计算或导出时读取相应明细。验收时需同时核对历史值、完整导出和有零值的稀疏矩阵。

四个小规模整数规划验证了这组并发请求下的结果一致性。大型 MIP、非线性求解、不同生产商的模型延迟和生产流量需要各自的工作负载来确定容量。
