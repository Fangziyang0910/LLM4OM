Feedback Repair

求解后对照原题复核，并按具体问题修正。

本页内容

Feedback Repair 在 Direct 的一次生成之后加入实际求解、对照原题复核和定向修复。它关注一个常见问题：程序能运行、求解器也说最优，但模型可能把业务规则写错了。

为什么求解成功之后还要检查#

如果题目要求 B 至少生产 3 件，而代码写成 B <= 3，生产案例仍会返回利润 13 的最优方案 (3, 2)。这个结果对错误模型是正确的，却违反原需求。只修复 Python 异常发现不了这种错误。

复核节点读取原题、数学模型、代码、执行反馈和可用冲突诊断，检查目标系数、变量域、约束方向和数据绑定。它应指出具体不一致，再决定接受或修复。

执行流程与逐步案例#

跟着案例看流程
1. 初次建模

假设这次生成把最低需求的方向写反。求解器不读取题意，因此仍可能报告最优。

原要求：B ≥ 3
假设误写：B ≤ 3
错误模型最优：A = 3，B = 2，利润 13
2. 对照复核

检查者指出原题与代码的具体差别，并将其写入修复反馈。

判断：repair
原因：最低产量要求写成上限，B = 2 违反 B ≥ 3。
3. 修复重算

改回 B ≥ 3，保留其他要求，再执行新代码。

2A + B ≤ 8；A + 2B ≤ 8；B ≥ 3
整数最优：A = 2，B = 3，利润 12
4. 接受或报告

利润下降是满足要求的代价。通过后结束；次数用尽仍有具体错误，则保留结果并报告失败。

原方案利润 13；满足 B ≥ 3 后利润 12。
两份模型与结果可分别查看。

教学案例：用示例输入和中间产物逐步说明流程。

应该修什么#

反馈合理处理
语法错误、返回对象不符合契约按执行反馈修复代码
整件产品被写成连续变量修复变量域并重算
真实需求与资源冲突接受经复核的不可行结果并保留原要求
时间上限内只有可行解保存当前状态与已有可行方案
满足性问题没有目标值核对它是否本来只需满足约束

次数与最终产物#

最多修复三次。格式、执行和建模修复共享同一个三次预算。无需修复时，方法使用两次大模型调用和一次求解；平台的方案解读可能另有调用。

后续回复不完整时，保留最后一次实际执行的模型、代码和结果。复核调用失败或回复无法解析，也保留已完成计算，并说明复核失败。

怎样使用与阅读过程#

在运行设置选择 Feedback Repair。看第一次生成、复核理由和改动位置。每次修复都可以沿反馈理由找到对应规则和代码位置。

它适合用简短流程增加一次结果后核对的场景。分层验证见 TriVAL；逐约束回译和冻结已通过组件见 SAC-Opt。

实现来源#

由本项目维护，复用 Direct 的生成提示。复核节点和修复循环的实现与生成提示一并公开。

当前参数#

以下取值来自方法预设，随每次运行保存。管理员可在部署预设中调整预算与重试次数。
