选择建模方法

比较 13 种方法的流程、问题范围和使用方式。

本页内容
按流程特征选择怎样配置和比较研究方法在平台中的含义

建模方法决定大模型怎样形成数学模型和代码，以及何时验证、调试或继续搜索。它与大模型预设、建模库和求解后端分别配置。

按流程特征选择#

第一次体验可以从 Direct 开始；需要求解后复核时看 Feedback Repair。要研究具体机制，可以根据下表进入对应方法。这里按流程分类，不是准确率排名。

方法核心流程显式问题范围
Direct一次生成模型与代码由方法提示、库和后端共同决定
Feedback Repair生成、求解、对照原题复核与修正同上
TriVAL语义、数学模型、代码三阶段验证同上
OptiMUS 0.3分项提取、逐条建模、组装与调试LP/MILP
Chain-of-Experts协调者依次选专家，汇总建模LP/MILP
OptiTree类型树匹配、思路检索、代码检查LP/MILP
OR-LLM-Agent数学模型、代码、执行与复查LP/MILP
ORThought建模思路、数学模型、代码与错误调试由方法提示、库和后端共同决定
LLMOPT五要素模型与自我校正同上
AutoFormulation组件建树、MCTS、模型排名LP/MILP
SAC-Opt语义锚点、回译、选择性修正LP/MILP
BIND数据结构、完整数据绑定、执行修复由方法提示、库和后端共同决定
OptiMind公开类型提示与多轮反馈同上

怎样配置和比较#

在运行设置中选择方法，或在 Chat Agent 消息中明确指定。13 个内置方法都接受九个建模库，但某个库能否表达问题、后端能否求解，以及方法本身的问题范围仍需同时满足。

参数由部署预设固定，每篇方法文章的参数表从当前代码生成。单次运行不能通过界面、CLI 或 Python 修改这些参数；实际快照保存在运行配置中。用方法对比可以保持问题与环境不变，检查不同方法的实际行为。

研究方法在平台中的含义#

平台保留已移植方法的核心编排、提示和停止条件，并记录代码契约与执行环境适配。SAC-Opt 是独立实现；BIND 和 OptiMind 有明确的公开范围与部署适配。各篇文章分别说明，不能把所有方法都描述为逐字移植。

方法使用你配置的 LLM。接入一套推理流程不等于使用了论文训练模型，也不等于复现其评测成绩。每次运行的实际模型、参数、步骤和结果才是检查该次行为的依据。

↗Direct一次生成数学模型与求解代码，再交给求解器计算。↗Feedback Repair求解后对照原题复核，并按具体问题修正。↗TriVAL依次验证语义、数学模型与代码，必要时回溯修订。↗OptiMUS 0.3提取参数、目标和约束，逐项建模并组装代码。↗Chain-of-Experts协调者依次选择专家，汇总意见后生成模型和代码。↗OptiTree沿问题类型树匹配建模思路，再生成并检查代码。↗OR-LLM-Agent先建立数学模型，再写代码，结合执行反馈修复与复查。↗ORThought按建模顺序写出思路、数学模型和代码，并调试执行错误。↗LLMOPT构造五要素模型，再根据自我校正回到相应步骤。↗AutoFormulation搜索多个模型组件，用 MCTS 和两两比较选择完整模型。↗SAC-Opt提取语义锚点，回译约束代码，只修正未通过的组件。↗BIND向模型提供数据结构，由求解代码读取完整附件。↗OptiMind结合公开类型提示与多轮求解反馈检查模型。
