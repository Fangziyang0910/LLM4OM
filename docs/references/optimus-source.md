# OptiMUS 固定源码观察

本文描述上游固定代码。当前平台编排与差异见[方法说明](../development/methods.md)。上游行为、论文算法和平台变体分别标识。

## 固定来源

来源为 [optimus-v0.3 的 e182e9e](https://github.com/teshnizi/OptiMUS/tree/e182e9ef5841605c2a7e87467021fd83522b6484)。考察覆盖入口、参数/约束处理、代码组装、执行调试及相关提示。固定文件与许可身份保存在项目的 OptiMUS source manifest 中。

main README 所列论文版本与分支分别对应。只读主分支 README 不能确定 v0.3 的实际流程。代码许可为 MIT，数据和检索材料的许可另行核对。

## 入口与阶段

固定 main 接收公开参数及 labels，逐条处理约束，维护问题状态，再形成代码和执行反馈。它没有把任意自然语言自动转换成这些外部文件。

| 操作 | 源码观察 |
|---|---|
| 参数整理 | 读取提供的值与元数据 |
| 目标/约束提取 | 形成后续逐条处理的状态 |
| 约束建模 | 每条约束独立生成数学声明，维护变量和辅助约束 |
| 代码生成 | 将完整参数/变量字典提供给各条代码提示 |
| 代码组装 | 合并已生成片段 |
| 执行调试 | 非零退出时，将描述、最新代码和 stderr 送入调试提示 |

固定执行函数最多运行三次脚本，最终仍可能生成一份未再次执行的修复。保存“最新代码”与实际已执行代码需要分别处理。

检索模式和模板调用需要按实际分支检查。导入检索模块或存在数据库不表示每次提示都使用了检索结果。检索内容和权限不能由目录名推断。

## 与论文的关系

[论文 v3 的方法章节](https://arxiv.org/html/2407.19633v3)描述逐条建模、连接图、结构识别及更多调试步骤。固定 main 保留逐条框架，但没有完整连接这些组件，执行次数与阈值也不同。

因此，该固定代码不能证明完整复现论文算法。当前平台进一步使用自然语言提取和可配置模型工厂，明确记录为流程变体。

## 可迁移认识

逐条形成数学声明有助于保存约束来源。全量状态和局部提示的职责要分清。代码修正需要关联原表述和实际执行反馈，最终选择只能使用确实检查过的产物。

这些认识来自源码观察。平台是否可用由真实方法/求解路径的验证确定，见[支持验证](../development/validation.md)。
