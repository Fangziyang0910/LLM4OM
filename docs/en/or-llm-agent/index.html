OR-LLM-Agent

Build the formulation first, then generate, execute and recheck code.

On this page

OR-LLM-Agent builds a formulation before generating and executing code. Its main round, infeasibility check and recheck have separate budgets, allowing execution feedback to inform later modeling decisions.

Why separate formulation and code#

A separate formulation gives readers a checkpoint without having to recover business meaning from Python. When execution fails, inspect whether code deviates from the formulation or the formulation itself needs revision.

In transport, establish warehouse supply limits, store demand and the cost objective first. A transposed cost matrix is an implementation issue; reversed demand inequalities require formulation review.

Workflow and feedback example#

FOLLOW THE EXAMPLE
1. State the rules

Check supply and demand directions. Whether excess delivery is permitted must come from the problem.

sum_j x[i,j] ≤ supply[i]
sum_i x[i,j] ≥ demand[j]
min sum_i,j cost[i,j] × x[i,j]
2. Locate runtime errors

If cost[j][i] causes an index error, use the data orientation in execution feedback to repair indexing.

Hypothetical error: costs indexed store-first.
Actual data: warehouse rows, store columns.
3. Interpret the result

Supply below hard demand can be genuinely infeasible. Distinguish a data conflict from a modeling error.

Total supply 10, required demand 12 → shortfall 2.
Review the supply limits, demand constraints and attached quantities.
4. Check code versions

Upstream round behavior can leave the final proposed repair unexecuted. Numerical results must stay attached to executed code.

Intermediate artifact: latest repair proposal
Numerical result: last actually executed model
Run steps identify which code versions were executed.

Worked example: illustrative inputs and intermediate artifacts.

Separate attempt budgets#

The preset assigns main 3, infeasibility 1 and recheck 2 attempts. Repairs use copied conversations; only the final code returns to the main conversation. Read each round together with its actual execution record.

Difference from Chat Agent#

“Agent” here names a fixed modeling method. Chat Agent is the user-facing optimization conversation. It can call Direct, TriVAL or other methods and handles explanations, plan selection and scenarios. You can request OR-LLM-Agent as the modeling method within Optimization chat.

When to use it and what to inspect#

The method targets LP/MILP. Use it to inspect an explicit formulation followed by execution repair and rechecking. Locate the last actual execution first; inspect its code, status, objective and variables before reading later repair suggestions.

Source and platform adaptation#

The platform ports the pinned OR-LLM-Agent implementation, retaining prompts and recovery paths. Native build_model(data) contracts replace Gurobi-specific requests. Final repair proposals and actual executions retain their respective artifacts.

Current parameters#

These values come from the method preset and are saved with each run. Administrators can change the deployment preset to adjust budgets and retry counts.
