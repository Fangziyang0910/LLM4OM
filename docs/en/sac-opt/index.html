Modeling methods/SAC-Opt

SAC-Opt

Extract semantic anchors and selectively repair constraints after backtranslation.

On this page

SAC-Opt preserves business meaning as semantic anchors, translates constraint code back into language, and compares that translation with the anchors. Failed constraints are repaired selectively; accepted components are frozen.

Why read code backwards#

“Each employee works at most five days” requires summing over dates. Summing over employees can instead mean “at most five employees per day.” Both programs may execute while expressing different rules.

The backtranslator reads constraint code and context to state its expressed rule. A comparator checks that translation against the original semantic anchor and returns a pass or repair decision.

Workflow and constraint-level example#

FOLLOW THE EXAMPLE
1. Keep anchors

Define binary x[e,d] for employee e and date d. Preserve requirements with their quantifiers and index meanings.

x[e,d] = 1 if employee e works on date d.
C1: each employee works at most 5 days.
C2: at least 3 employees each day.
2. Backtranslate

Suppose C1 mistakenly sums over employees. The translation reveals that it actually limits daily headcount.

Hypothetical error: for each d, sum(x[e,d] for e in E) ≤ 5
Translation: at most 5 employees each day.
3. Selective repair

Repair C1's quantifier and summation direction. Freeze C2 if it passed, avoiding unrelated rewrites.

Repair C1: for each e, sum(x[e,d] for d in D) ≤ 5
Freeze C2: for each d, sum(x[e,d] for e in E) ≥ 3
4. Assemble and run

Assemble checked components and execute the complete model. Preserve an explicit unresolved status if semantic checks exhaust their budget.

Semantic consistency: recorded per constraint
Executability: checked on the complete program
Numerical plan: returned by the actual backend

Worked example: illustrative inputs and intermediate artifacts.

From four anchor types to code#

Parameter and variable anchors capture symbols, shapes, units, domains and bounds. The current implementation retains parameters and variables with confidence scores above 3; low-confidence constraints receive further assessment. Code is generated as setup, objective and individual constraints, with component counts checked against anchors.

Full attachments remain accessible through build_model(data). Submitting several components together changes orchestration, not the unit of judgment: each constraint still receives its own consistency decision.

Limits and failure interpretation#

Defaults allow five parse attempts, five semantic rounds and three full-program executions. Semantic checking and execution debugging are separate loops: one checks meaning, the other handles runtime failures.

A repair produced after the final failed comparison cannot be presented as independently passed. The platform keeps unresolved failures alongside actual solver results. Inspect both the failed constraints and the code associated with the numerical result.

When to consider this workflow#

Use it for LP/MILP problems with many rules, fragile indices or quantifiers, and a need to inspect individual constraints. It does not judge model quality from objective values alone. Compared with TriVAL, its focus is anchor-to-constraint-code consistency. Compared with Feedback Repair, repair is more granular.

Platform implementation and sources#

This is an independent implementation of the published algorithm, using prompts written by this project. The pinned reference is Forrest-Stone/SAC-Opt. The platform retains anchors, blind backtranslation and selective repair, with batched components and native-model contracts. The published source records the component and contract adaptations.

Current parameters#

Parameters come from the deployed method preset. They are saved with each run and cannot be changed per run in the UI, CLI or Python API.
