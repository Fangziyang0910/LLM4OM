Modeling methods/OptiMUS 0.3

OptiMUS 0.3

Extract parameters, objectives and constraints, then assemble component code.

On this page

OptiMUS 0.3 constructs a model component by component. It extracts parameters, objectives and constraints, formulates and codes individual components, then assembles and executes them. Intermediate artifacts make a long generation task easier to inspect.

From rules to components#

“Only 8 cutting hours” is a business rule; 2A+B≤8 is its formulation; a native Constraint is its implementation. OptiMUS keeps these stages visible so readers can follow changes in meaning.

Objectives and constraints are handled separately. Constraints receive redundancy and confidence checks. A low-confidence item can be retained, removed or modified. These are LLM judgments: check whether removal eliminates a duplicate or loses a distinct requirement.

Workflow and worked example#

FOLLOW THE EXAMPLE
1. Parameters and rules

Identify profit, resource consumption and capacities as parameters. Two resources are not duplicates merely because both capacities equal 8.

Profit: A=3, B=2
C1: cutting capacity 8, consumption (2,1)
C2: finishing capacity 8, consumption (1,2)
2. Check components

Repeated wording can be removed. Cutting and finishing have different coefficients and remain separate constraints.

C1 → 2A + B ≤ 8
C2 → A + 2B ≤ 8
Preserve nonnegative integer domains.
3. Assemble code

Components enter one build_model(data). Names, indices and parameters must agree across components.

setup + variables + C1 + C2 + objective + return model
Generated code builds; the platform solves.
4. Execute and debug

The correct model gives A=3, B=2 and objective 13. If debugging occurs, check that changes preserve component meaning.

At most 3 execution/debug attempts
Infeasible or unbounded statuses can also trigger debugging.

Worked example: illustrative inputs and intermediate artifacts.

Parameter data and confidence#

An attached params.json in the upstream format supplies parameters directly. Otherwise the method extracts them, including values, from the problem. An unknown business quantity must not become an invented fixed parameter.

Constraint confidence uses five-point judgments with bounded retries. Low-confidence items receive further feedback deciding retention, removal or revision. The process retains those decisions and the updated list.

How its repair differs#

Execution debugging treats optimality as success and also preserves explicitly local optimality from compatible backends. Infeasible and unbounded models can therefore enter debugging. Feedback Repair instead permits a reviewed, genuinely infeasible model to end normally.

When infeasibility is plausible, check whether debugging changes a hard requirement. For checking code against individual constraint meanings, see SAC-Opt.

Scope and reading a run#

The current method targets LP/MILP. Follow a rule through parameters, description, formulation, code and execution. More rules require more component calls. Defaults use temperature 1.0 and at most three execution/debug attempts. RAG and interactive human confirmation are not enabled.

Source and adaptation#

The platform ports the pinned OptiMUS v0.3 implementation, retaining the component workflow and prompts while supplying native-library components and a sandbox. Delimiter and code-block parsing fixes preserve generated content. Detailed changes are linked in the source documentation.

Current parameters#

Parameters come from the deployed method preset. They are saved with each run and cannot be changed per run in the UI, CLI or Python API.
