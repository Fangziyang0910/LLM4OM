Modeling methods/ORThought

ORThought

Write a reasoning path, formulation and code, then debug execution errors.

On this page

ORThought asks the LLM to state a modeling path in an expert-like order, then provide the formulation and code. The path is retained so readers can understand why variables, objectives and constraints were chosen.

What a useful modeling path explains#

Useful explanations name concrete choices: “whole products require integer quantities” or “processing hours add across products, so capacity is consumption times quantity.” The path links each business rule to its variable domain or mathematical expression.

The current workflow uses the upstream formalized mode and outputs a modeling path, formulation and code. The process view retains this explanation as a separate solution_path artifact.

Workflow and modeling-path example#

FOLLOW THE EXAMPLE
1. Identify decisions

Separate production decisions from known inputs.

Decide production quantities A and B.
Profit, processing times and capacity are given parameters.
2. Explain expressions

Connect each expression to its business meaning instead of listing unexplained formulae.

Whole units → nonnegative integer A, B
Additive hours → 2A+B≤8, A+2B≤8
Total profit → max 3A+2B
3. Check execution

If code cannot obtain a solver status, debugging reads the problem, formulation, code and actual error.

Execution error → at most 3 code-debug attempts
Valid infeasible status → no debugging solely for infeasibility
4. Read back results

The correct integer optimum is 13. Substitute actual values into resource expressions to check the explanation.

A=3, B=2
Cutting 8; finishing 7; profit 13
Explanation must agree with these actual values.

Worked example: illustrative inputs and intermediate artifacts.

Execution repair versus semantic checking#

Code that cannot obtain a solver status enters debugging, up to three times. Successfully executed code returning infeasibility does not trigger debugging simply for lacking a feasible solution. This differs from OptiMUS.

For explicit review against the problem see Feedback Repair; for layered validation see TriVAL.

When to use it and how to read it#

Use it when a retained modeling explanation helps learning and inspection. Choose the library and backend for your variable domains and expressions using the solver guide. The saved path, formulation, code and values can be read together.

Source and platform adaptation#

The platform ports the formalized workflow from the pinned ORThought implementation. It returns native models, executes in the sandbox and retains solution_path.

Current parameters#

These values come from the method preset and are saved with each run. Administrators can change the deployment preset to adjust budgets and retry counts.
