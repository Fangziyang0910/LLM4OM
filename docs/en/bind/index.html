Modeling methods/BIND

BIND

Show data structure to the LLM and read complete attachments during execution.

On this page

BIND separates understanding data structure from reading complete values. The LLM sees fields, types and sizes; generated code reads the full JSON/CSV during execution. This addresses truncated previews, long-table transcription and data-binding errors.

Why structure can be enough#

Model structure often does not depend on every individual value. A transport model needs to know that costs form a warehouse-by-store matrix and demand is indexed by store. It need not copy every matrix entry into a prompt and back into code.

Structure does not replace meaning. The problem must still explain whether capacity means hours, units or vehicle load. Field names alone cannot reliably specify all business rules.

How data flows#

FOLLOW THE EXAMPLE
1. Prepare data

Upload structured data and explain units and index meanings in the problem.

production.json
profit: profit per unit, indexed by product
usage: resource-by-product hours per unit
capacity: available hours per resource
2. Provide structure

Generation receives field structure, including nested and irregular shapes.

profit: array[number], length 2
usage: array[array[number]], 2 rows
capacity: array[number], length 2
3. Bind at execution

Code parses complete file text from data and constructs expressions from those values.

payload = json.loads(data['production.json'])
profit = payload['profit']
usage = payload['usage']
capacity = payload['capacity']
4. Check and repair

Format and execution errors can trigger retries. Genuine infeasibility is a valid status, not permission to relax requirements.

At most 3 generation/execution attempts.
Check row/column meaning and units, not just successful parsing.

Worked example: illustrative inputs and intermediate artifacts.

A ready-to-use example#

{
  "products": ["A", "B"],
  "profit": [3, 2],
  "usage": [[2, 1], [1, 2]],
  "capacity": [8, 8]
}

Describe it as: “usage[r][p] gives hours of resource r per unit of product p. capacity[r] is available hours. Choose nonnegative integer quantities to maximize total profit without exceeding any resource.” The correct result is A=3, B=2, objective 13. The data editor example demonstrates editing while preserving original result snapshots.

Supported inputs and information boundaries#

JSON and CSV are supported; the frontend converts Excel to CSV. CSV headers and row widths are checked before LLM calls. Heterogeneous nested JSON is not presented as a rectangular matrix. Without attachments, the method uses the problem directly. It adds no PDF or image parser.

Generation receives schema; execution reads complete attachments. Later feedback can include actual objectives and decision values.

When to use it and what to check#

Use it for structured data too large to transcribe conveniently when rules are clear. Inspect file names, fields, matrix orientation, units and iteration over all records. For semantic review of complex rules, compare with Feedback Repair or TriVAL.

Source and platform adaptation#

Based on schema offload and the default agentic path in the pinned Text2Opt-Bench implementation. User attachments replace benchmark data; reference-optimum and model-size scoring are removed. The platform returns a formulation and native model code, repairing according to actual execution status.

Current parameters#

Parameters come from the deployed method preset. They are saved with each run and cannot be changed per run in the UI, CLI or Python API.
