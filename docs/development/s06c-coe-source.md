## Finding

The fixed implementation selects experts sequentially, shares their comments, reduces them to Python, and optionally performs execution-based reverse blame/refinement. Preserve these operations inside one Method adapter. **Its backward refinements do not survive the next trial's fresh comment pool.** The returned answer is the last reducer response, not a refined answer or best-scoring candidate. Source fidelity must expose this behavior; carrying corrections forward is a named workflow variant. Do not substitute Direct, a fixed expert chain, or a single-shot prompt. [main][main], [routing][conductor], [reducer][reducer].

The method yields source-native function code, not a `build_model(data)` factory. A Modeling Expert comment may contain mathematical text, but that expert is optional and its comment is not a guaranteed final formulation. Preserve native output and mark Formulation unavailable where faithful extraction is absent. [expert model][modeling], [programmer][programming], [main][main].

## Actual entry, defaults and budgets

`chain_of_experts(problem, max_collaborate_nums, model_name, enable_reflection, max_trials)` has no argument defaults. Positive collaboration/trial values are checked even when reflection is disabled. The `main.py` demonstration loads LPWP `prob_250` and requests `gpt-3.5-turbo-1106`, reflection off, but omits both required limits: as written it raises a missing-arguments error before entering the workflow. The usable intended experimental entry is `run_exp.py`, which supplies all arguments. [main][main], [experiment entry][runexp].

`run_exp.py` defaults: model `gpt-3.5-turbo`, collaboration limit 3, trials 3, reflection **off**, log directory `log`. Dataset, problem regex and algorithm are required. It checks the directory, sorts matching problem directories, and invokes CoE once per matching directory. It saves the original answer and extracted code, rewrites `generated_code.py`, then runs the separate benchmark test. Its ten-second sleep after CoE is pacing, not an algorithm stage. README lists some algorithm choices absent from actual argparse choices; use source choices. [run_exp.py][runexp], [README][readme].

All roles use the supplied model with `temperature=0`. BaseExpert concatenates `ROLE_DESCRIPTION`, a newline and `FORWARD_TASK`/`BACKWARD_TASK`, then uses LangChain `PromptTemplate | ChatOpenAI`; this is text prompting, not native tools or JSON response mode. Conductor alone sets output `max_tokens=10`. Other output caps, provider retries, timeout and total token/cost limits are not explicitly set in these sources; package defaults cannot be reconstructed into a fixed budget without a runtime lock. `langchain==0.1.11`, `langchain-community==0.0.27`, `gurobipy==10.0.2` are pinned, but `langchain_openai`/`langchain_core` are imported without explicit version pins and NumPy/tqdm are unpinned. [base][base], [conductor][conductor], [requirements][requirements].

Let `k=min(max_collaborate_nums,7)` and `T=max_trials` with reflection, otherwise `T=1`. Each completed forward trial makes `2k+1` model calls: k conductor, k expert, one reducer. Reflection adds one generated-test call and zero to k backward calls. Bounds excluding provider retries are `T(2k+1)` without the added reflection calls, and at most `T(3k+2)` with reflection. Default non-reflection is 7 calls; reflection with k=3,T=3 can reach 33, including backward work on the final failed trial. There is one public import/function-check attempt per reflected trial, not a fixed number of Gurobi solves. [main][main], [evaluator][evaluator].

## Full participating roles and prompt inputs

The seven-element order below is the **registry and substring-matching order**, not an enforced invocation order. All forward expert calls except Terminology Interpreter insert the current chronological comment text. CommentPool renders each item as expert name plus fenced comment; an empty pool has an explicit no-comment sentence. Main supplies all-ones visibility, and these experts call `get_current_comment_text`, which itself does not apply the visibility matrix. [main][main], [pool][pool].

| Registered role | Actual forward task / inserted inputs / state |
|---|---|
| Terminology Interpreter | Description and literal knowledge `None`; asks for at most three hard terms as JSON. `comments_text` is passed but has no template placeholder, so prior comments do not reach this prompt. Parses JSON/list or falls back to raw text, renders term/interpretation lines, saves `previous_answer`. [source][terminology] |
| Parameter Extractor | Description plus comments; extracts variables, constraints and objective suitable for LP/MIP; rejects strict inequalities in its instruction. Free-text reply saved as `previous_answer`. Its routing description misleadingly describes programming. [source][parameter] |
| Modeling Expert | Description plus comments; requests JSON string fields `VARIABLES`, `CONSTRAINS` (actual spelling), `OBJECTIVE`. Performs literal spaced `<`/`>` replacement with non-strict LaTeX comparisons; does not parse or validate mathematical semantics. Saves `previous_answer`. [source][modeling] |
| Programming Example Provider | Description, supplied `code_example`, comments; generates problem-specific Python. No retrieval or external example lookup exists. Saves `previous_code`. [source][example] |
| Programming Expert | Same input fields; asks for strict starter-function format, imports only outside function, no tests, LP/MIP. Mentions Gurobi but also NumPy/SciPy/PuLP; source does not guarantee gurobipy-only output. Saves `previous_code`. [source][programming] |
| Modeling Knowledge Supplement Expert | Despite its name, asks for Python using description, starter and comments, not a knowledge-store lookup. Saves `previous_code`. Its routing description duplicates programming. [source][knowledge] |
| Code Reviewer | Description plus comments; reviews code, errors, efficiency and improvements. Starter is not directly inserted. Saves `previous_code`. Routing description also duplicates programming. [source][reviewer] |

Every participating expert implements a backward prompt with original description, its stored previous answer/code, and accumulated feedback. It asks for `is_caused_by_you`, `reason`, `refined_result`; some examples use single-quoted Python dictionaries rather than strict JSON. Parsing can accept Python literals. Backward output is not automatically extracted into code. A refined comment does not update the expert's stored previous-answer attribute. [role sources above], [parser][utils], [main][main].

Conductor receives description, all expert names/descriptions, already-commented names, remaining names, total and remaining collaboration count. It **does not receive the actual comment contents**. It first picks the first remaining expert whose full name occurs in its reply; then scans all experts, allowing repeats if only an already-used name matches. Invalid routing uses `random.choice` over remaining experts, or all experts if none remain, without a seed. Neither non-repetition nor semantic routing validity is guaranteed. [conductor][conductor].

Reducer's internal name is `Solver`, but it is an LLM summarizer, not the numerical Solver plugin. It sees description and all comments, not starter directly; it requests final function code with imports but no test code. There is no requirement that Modeling Expert or Programming Expert must have been selected before it runs. LPFileGenerator is imported but commented out of the participating list; its LP-format knowledge is literal `None` if called separately. Do not add it or imagined paper agents to this integration. [reducer][reducer], [main][main], [disabled LP role][lp].

## Iteration, execution, extraction and failure selection

Each trial allocates a fresh comment pool and expert stack, makes exactly k selections, adds each comment, then reduces. It extracts code and overwrites `generated_code.py`. Expert objects persist between trials, but the next forward calls overwrite their previous-answer attributes; no previous feedback enters the next forward prompts. [main][main].

With reflection on, Evaluator generates one JSON test input from description and starter. Its template contains one fixed candy example; that example belongs to prompt identity, not a benchmark oracle. It accepts the first item of a nonempty list or a dict with `input`; malformed output raises. Evaluation imports **and reloads** `generated_code`, potentially executing top-level code twice, finds the first alphabetically inspected function named `prob_*`, and calls it using generated keyword arguments. It ignores returned values. Import or invocation errors produce traceback feedback; absence of a `prob_*` function raises uncaught `NotImplementedError`. Thus the inspected ComplexOR `aircraft_assignment` function name cannot pass this reflection function-discovery rule unchanged. [evaluator][evaluator], [ComplexOR starter][aircraft].

On no exception, feedback is `None` and the trial loop ends. On feedback, main creates a separate feedback pool seeded with Evaluator, pops selected experts and matching comments in reverse order, and invokes backward. A parse failure adds the raw result as feedback and continues. A parsed truthy `is_caused_by_you` restores that expert's comment using `refined_result`, pushes it back, and ends the reverse walk. Otherwise `reason` is added for earlier experts. No reducer rerun follows this correction; the next outer trial discards both pools. The final failed trial can perform backward calls and still return its pre-refinement answer. Evaluator feedback is rendered by `get_current_comment_text`, avoiding the name-index lookup that would not know Evaluator. [main][main], [pool][pool].

Extraction used by main/run_exp is `utils.extract_code_from_string`: no fenced block means raw answer; one block means its body; multiple blocks are joined after removing any block containing `pip`. It is not the stricter unrelated extractor in `extract_program.py`, which is an offline top-level script that writes reference-program files and is never invoked by this workflow. JSON parsing tries raw text, extracted code and first balanced object/list, then `json.loads` and `ast.literal_eval`, with optional expected type. Preserve raw reply, extracted bytes and parser outcome separately. [utils][utils], [offline extractor][extractprogram].

There is no best-of-trials selector or hidden-score feedback in `chain_of_experts`: first exception-free public check stops it, otherwise last reducer wins. For platform outcome semantics, exhausted reflected trials should retain the source-selected last candidate **and its public failures**, reporting exhaustion rather than success. Non-reflection selects last/only reducer without public checking. Malformed test generation, missing function or LLM exception can abort; do not silently convert these into a new model fallback. [main][main], [evaluator][evaluator].

## Dataset loader, public projection and provenance

`read_problem(dataset,problem)` reads exactly `dataset/<dataset>/<problem>/description.txt` and `code_example.py`, returning `{description,code_example}`. It does not read samples, solutions, parameters or GT models. `read_test_samples` independently loads `sample.json`. The outer benchmark imports the function named exactly as the problem directory, can import optional `data_process.py` and apply `post_process`, then compares the returned scalar/tuple with `sample.output` using exact equality. Runtime error takes precedence over accept/wrong-answer; empty samples would vacuously accept. This benchmark is distinct from the public Evaluator. No `data_process.py` appears under fixed ComplexOR. [loader][utils], [benchmark][testgenerated], [run_exp][runexp].

Fixed tree inventory: **288 LPWP problem directories, 18 ComplexOR directories**. These are directory counts, not validated benchmark sizes or the paper's 37 problems. Also present: ComplexOR_raw/backup, NLP4LP, NL4Opt, Mamo, IndustryOR, ReSocratic. The loader has no split projection, dataset version/manifest validation, license filter or transformation provenance. No train/dev/test manifest or source-origin license was found in this fixed tree; do not invent split membership or treat the extra datasets as supported CoE imports. README calls ComplexOR a raw release and says the formal 37 will follow. [fixed dataset tree](https://github.com/xzymustbexzy/Chain-of-Experts/tree/afb89bf602690ea621f13a23c42722f20f653a43/dataset), [README][readme], [loader][utils].

Byte inspection was bounded to LPWP `prob_0` description/starter/sample, LPWP `prob_250` starter, and ComplexOR `aircraft_assignment` description/starter/sample. **These starters are task-specific function signatures/docstrings with placeholder returns**, not generic unrelated public examples and not complete reference solutions. They disclose argument semantics and return conventions, which are additional modeling input. Some placeholder values must not be mistaken for an oracle objective. Both inspected sample files are lists with `input` and `output`; `input` keys follow those signatures. This does not prove that all other starters are safe or licensed. [LPWP starter](https://github.com/xzymustbexzy/Chain-of-Experts/blob/afb89bf602690ea621f13a23c42722f20f653a43/dataset/LPWP/prob_0/code_example.py), [demonstration starter](https://github.com/xzymustbexzy/Chain-of-Experts/blob/afb89bf602690ea621f13a23c42722f20f653a43/dataset/LPWP/prob_250/code_example.py), [ComplexOR starter][aircraft].

Minimum Task Adapter projection: retain description and only an audited, explicitly public starter/interface artifact, with original bytes/hash, source commit/path, signature and permission evidence; independently declare any public instance input values. Keep sample outputs, GT models, solutions and reference implementations private. Sample inputs are not automatically public merely because they occur beside outputs: if a task revision deliberately projects them as instance data, record that decision and changed input conditions. Missing/unsafe starter means `needs_input` for the source-input variant, or an independently authored starter and explicit input variant. Existing unlicensed dataset records are research evidence, not fixtures to copy into the repository. A new self-authored public LP/MILP problem and starter can demonstrate S06-C without claiming dataset integration. [contracts](../plugin-contracts.md#33-evaluationcase--evaluationoracle), [evaluation](../evaluation.md), [source loader][utils].

The primary paper link is [ICLR/OpenReview](https://openreview.net/forum?id=HobyL1B9CZ), as cited by fixed README. Forum/PDF requests encountered a browser challenge and API metadata returned 403 during this bounded investigation. No full-paper algorithm or experimental claim is attributed here as independently verified. The concrete divergences above are source observations; paper-specific identity remains a fidelity-report field, not a reason to synthesize missing agents. [README][readme].

## Minimum complete adaptation and interface work

At this baseline, the design contracts already describe public execution/artifact resources, but implemented `MethodContext` has only `llm`, byte-mapping `data`, `budget`, `problem_sha256`. `ModelProposal.formulation` is mandatory. Admission accepts three single-candidate profiles and demands five-element Formulation. Application accepts only selected candidate `001`, validates Formulation unconditionally, persists one candidate and encodes native gurobipy as `build_model` factory. Therefore S06-A native support is **not** general upstream-function/script support. [methods](../../src/llm4om/methods.py), [admission](../../src/llm4om/preflight.py), [application](../../src/llm4om/application.py), [implemented native contract](../plugin-contracts.md#11-s06-a-gurobi-and-native-code-sdk-060).
