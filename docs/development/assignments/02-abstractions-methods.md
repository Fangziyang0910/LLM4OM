# 任务书二 核心抽象复核与两种建模方法接入

执行人：同学 B。周期：第 11—20 天。起点：同学 A 已验收并合入的 `main`。

## 交付目标

复核并修正平台核心抽象，使问题、LLM、建模方法、数学表述、代码、建模后端和求解器的职责清楚。修复已确认的实现偏差，新增两种建模方法。其中一种固定为 LLMOPT，另一种自行选型。两种方法都须能从 CLI 和 Web 使用。

本阶段以当前 LP/MILP 范围和通用外部 LLM 为基础。保留方法的核心编排和阶段提示，不要求训练或完整复现原论文。

## 具体任务

1. **追踪并复核核心流程。** 从问题输入追踪到最终结果，核对 ProblemSpec、MethodContext、Formulation、Code、公开检查和最终选择。给出简洁的职责与数据流说明。纠正混用概念、重复校验和不必要的包装；不做无依据的整体重写。
2. **修复输入与产物的一致性问题。** 优先检查 JSON 回复抽取、无效或截断回复、数据视图不完整、数学表述与实际执行模型不一致等情况。非法外层 JSON 不能被悄悄替换为内层对象；部分数据不能被当成完整数据。明确缺失信息、合法不可行和代码错误的不同处理。
3. **复核现有七种方法。** 对照已有方法说明检查实际提示、阶段输入、反馈使用及最终选择。每种方法至少留下一个可重复检查。发现阶段未执行、数据未使用或反馈被忽略时，修复并补测试。方法名称和过程展示必须反映实际实现。
4. **接入 LLMOPT。** 围绕五元素表述、代码生成和执行反馈自修正组织流程。保留表述与代码的来源和修正关系。必须具有可识别的方法编排，不能仅把现有 Direct 或 Feedback Repair 改名。
5. **接入另一种建模方法。** 第 12 天结束前给出名称、论文或源码入口、核心流程及选型理由。要求与现有方法不重复，可使用自然语言和可选业务数据，不依赖专用训练权重。实现核心编排及阶段提示，记录固定来源、使用条件和适配差异。
6. **保持方法与求解器独立。** 两种新方法均使用配置的 LLM 和已有代码目标，优先接入共同 Pyomo 路径。方法内部不写死求解器；后续新增求解器应复用相同方法实现。变更字段时同步调用方、配置、前端和测试。

## 必要指引

从 [methods.py](../../../src/llm4om/methods.py)、[prompt_methods.py](../../../src/llm4om/prompt_methods.py) 和 [application.py](../../../src/llm4om/application.py) 追踪真实调用。依据[领域术语](../../../GLOSSARY.md)、[方法契约](../../contracts/methods.md)和[方法说明](../methods.md)核对职责。

LLMOPT 的依据见[论文](https://arxiv.org/abs/2410.13213)和[官方仓库](https://github.com/antgroup/LLMOPT)。本项目接入其通用 LLM 流程适配，需明确与原训练系统的区别。优先复用现有 Gateway、公开检查和记录机制。

Formulation 表达数学含义，Code 保存计算实现，求解器执行数值优化。严格 IR 是一种受支持的表示路径，不能为统一接口而强制全部方法改成同一种流程。

## 完成验收

- 两种新增方法均有独立配置、必要说明及真实阶段记录，CLI 与 Web 均能选择并运行。现有七种方法不退化。
- 九种方法在共同 Pyomo 路径上与现有三个求解器的 27 个组合通过流程检查。可以使用确定性 LLM 回复，但必须执行真实求解。
- 为新增两种方法各选至少 3 个小问题，使用实际 LLM 验证。两种方法都须覆盖 CLI 和 Web 入口；人工核对原问题、表述、代码和解，不只核对目标值。记录模型、预算、运行 ID 和失败原因。
- 建立或整理至少 12 个有独立预期的小型验收问题，覆盖目标方向、连续与整数变量、二元变量、常数项、数据输入、不可行和无界等情况，交给同学 C 复用。额外覆盖缺信息、错误回复及不完整数据的处理。
- 已确认的非平凡 bug 均有能复现原问题的回归测试。数学表述与执行模型不能因流程完成而被默认认定一致；展示来源和已有检查范围清楚。
- 新方法的主要改动落在自身实现、声明配置和测试中，核心调度不增加按新方法名称判断的特例。相关类型检查、回归与文档检查通过。
