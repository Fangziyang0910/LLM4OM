# 任务书三 两个求解器接入与全平台验收

执行人：同学 C。周期：第 21—30 天。起点：同学 B 已验收并合入的 `main`。

## 交付目标

新增两个求解器，完成真实执行接入和标准化结果处理。整合前两阶段成果，验证九种建模方法、五个求解器及 CLI、Web 两种入口，修复影响主流程的剩余问题，交付可在本机继续开发的平台。

新增求解器名称自行选择，不预先规定。当前范围仍是 LP/MILP、本机后端与单用户 Web，不增加公网部署或多平台适配任务。

## 具体任务

1. **选择两个实际新增的求解器。** 第 22 天结束前给出名称、官方资料、支持范围、依赖、许可及选型理由。选择本机可真实验证、适合现有 LP/MILP 路径的实现。不能仅给现有求解器换名称或包装；通过已有库接入新的求解引擎时，仍需独立声明、配置和真实验收。
2. **接入共同执行路径。** 通过现有 SolverBackend 及受支持的模型接口接入，优先复用共同 Pyomo 路径。补齐插件声明、依赖、Worker 构建、配置预检和示例。不为每一种建模方法各写一套求解逻辑，也不要求用户手工修改生成代码。
3. **正确提取真实求解结果。** 核对变量映射、目标方向、常数、最优状态、不可行、无界、时间限制和可行解存在性。保存实际求解器身份与版本。没有解时不填造目标和决策值；未知 bound、gap 或资源量保持未知。结果来自真实接口或受控结果文件，不能来自生成代码的自报输出。
4. **贯通 CLI 与 Web。** 新方法和新求解器在两种入口使用相同配置语义。页面可选择新增项，预检能报告缺失依赖和不兼容组合。方法、求解器、过程、最终结果、导出与历史版本保持一致。
5. **完成全平台复核与修复。** 复用前两阶段的验收问题和测试，检查输入、数据、配置、生成、执行、结果、取消、人工修改及记录读取。修复阻断使用和导致错误结果的问题。性能优化针对实测瓶颈，保留同一问题下的修改前后结果。
6. **整理最终交付。** 更新 README 的能力范围与使用命令，补齐新增项说明。用干净的一次性工作区从启动开始验收，保留测试命令、结果、运行 ID 和未解决项。最终更改集成到 `main`。

## 完成验收

- 两个新增求解器均完成真实安装、预检、模型构建和求解，具有可复用配置与清楚的使用条件。
- 九种方法与五个求解器在共同 Pyomo 路径上的 45 个组合通过流程检查。使用确定性 LLM 回复和真实求解器，核对实际配置、执行身份和结果；原生路径另按实际支持组合回归。
- 使用同学 B 提供的至少 12 个验收问题检查五个求解器。可行解需满足独立预期的域和约束，目标在声明容差内正确；多解问题不要求返回相同决策向量。不可行、无界和时间限制有独立检查。
- 两个新方法和两个新求解器均在 CLI 与 Web 完成端到端演示。两种入口使用相同问题、数据和配置时，其确定性结果及状态一致；真实 LLM 的不同采样分别记录。
- 完整 Python 回归、类型检查、前端构建、核心浏览器流程和文档检查通过。不能跳过新增求解器的真实测试，不能通过修改预期来掩盖错误；外部条件缺失单独说明。
- 从 README 命令可以启动后端和 Web；既有配置、设置及历史记录仍可使用或按已声明限制读取。最终 `main` 与远端一致，工作区干净。
