# 任务书二 整体前端重构与首组方法求解器接入

执行人：同学 B。周期：第 11—20 天。起点：同学 A 已验收并合入的 `main`。

## 交付目标

在已复核的流程和接口上，全面改善 Web 的布局、视觉、交互和产物阅读体验。完整接入 LLMOPT 和第一个新求解器，交付八种方法、四个求解器均可从 CLI 与 Web 使用的平台版本。

你负责本阶段的完整平台，前端是改进重点。新增功能、接口或抽象变化所需的后端、页面、配置和测试由你同步完成。接手时先复跑上一阶段验收问题，发现基线偏差也要定位和处理。

## 具体任务

1. **重构整体布局与视觉。** 围绕问题输入、建模过程、数学模型、求解代码和结果安排信息，统一排版、间距、对齐、按钮、表单及弹窗。普通操作直接可见，高级配置和原始诊断按需展开。提供整体布局改进，而非只调整配色。
2. **让建模过程和成果易于理解。** 保留同学 A 校正的真实步骤与产物关系，改善阶段浏览、修正记录和最终结果阅读。用户能够看清方法做了什么、产生了什么、为何修正、最终选择了什么。新增方法沿用同一展示入口，但保留自身实际编排。
3. **完成主要交互与状态处理。** 复核模型及密钥保存、方法和求解器切换、提交、澄清、取消、失败处理、历史版本和人工修改。区分新建与返回草稿，处理迟到响应和重复提交。通过共同类型与接口整理状态，减少按方法名称和文件名堆叠判断。
4. **完整接入 LLMOPT。** 依据其五元素表述、代码生成和执行反馈自修正的核心思路实现通用 LLM 流程适配，保留阶段提示、产物与修正来源。不能仅将已有方法改名，也不要求专用训练权重或完整论文复现。CLI、页面选择、过程展示和导出同时接通。
5. **完整接入第一个新求解器。** 第 12 天结束前给出名称、官方资料、支持范围、依赖、许可及选型理由。选择可在当前 LP/MILP 路径真实验证的新增实现，复用已有 SolverBackend 和 Worker。同步预检、依赖、配置、页面选项及结果标准化。
6. **通过扩展检验抽象。** 新方法使用配置的 LLM 与代码目标，新求解器复用现有方法，优先使用共同 Pyomo 路径。若接口确需调整，同次修改调用方、前端和测试，并更新必要说明。针对实测卡顿或重复请求做优化，保留前后对照。

## 必要指引

读[任务书一](01-baseline-and-method-audit.md)及交接结果，再从 [ProblemEditor.tsx](../../../frontend/src/components/ProblemEditor.tsx)、[RunView.tsx](../../../frontend/src/components/RunView.tsx)和[执行与求解](../solvers.md)追踪完整用户操作。LLMOPT 的依据见[论文](https://arxiv.org/abs/2410.13213)和[官方仓库](https://github.com/antgroup/LLMOPT)。

优先复用已有 Gateway、检查、记录及接口。新增步骤应能关联真实产物；不要只让页面显示一个新方法名称。第一阶段的接口是已有基线，仍可按实际需求修正，不能把不合理实现继续包装成约定。

## 完成验收

- 提供修改前后截图和完整操作演示。1280 与 1440 像素宽的桌面窗口中，布局完整、对齐清楚，用户能找到配置、过程和最终产物。
- 正常运行、无效输入、服务失败、澄清、取消、历史版本和人工修改有可重复检查。刷新及重启同一工作区后，配置与记录可恢复，密钥保持掩码展示。
- 逐一在新界面复核现有七种方法，确认实际步骤、中间产物和最终结果没有因 UI 重构丢失或错配，更新逐方法复核表。
- LLMOPT 在至少 3 个不同的小问题上使用真实 LLM 验证，覆盖 CLI 与 Web，由人核对各阶段数学含义及最终解。新求解器通过共用问题的真实求解，状态、变量映射、目标与常数处理正确。
- 八种方法与四个求解器在共同 Pyomo 路径上的 32 个组合通过确定性回复加真实求解检查。原生路径另按实际支持组合回归；新方法和新求解器均可在 CLI、Web 选择、运行并导出。
- 既有验收问题、受影响的 Python 与浏览器测试、类型检查及前端构建通过。源码、随包构建文件、配置和文档同步提交，不把接口接通或页面适配留给同学 C。
