## 30 天轮换开发任务

三位同学依次接手，每人 10 天。按三个可运行的平台版本交付，不按前端、后端或插件划分个人责任。每位同学都对当期完整流程负责，先复跑前一阶段，再改进、验证并集成到 `main`。

开始前，三人共同阅读三份任务书，并用同一个问题走通 CLI 与 Web，理解 30 天的整体目标和共同验收口径。每次交接由接手者复跑，不能只阅读上一位的完成报告。

| 执行人 | 周期 | 任务书 |
|---|---|---|
| 同学 A | 第 1—10 天 | [现有方法全链路复核与平台基线校正](assignments/01-baseline-and-method-audit.md) |
| 同学 B | 第 11—20 天 | [整体前端重构与首组方法求解器接入](assignments/02-workbench-and-first-extension.md) |
| 同学 C | 第 21—30 天 | [第二组方法求解器接入与平台整体验收](assignments/03-platform-and-second-extension.md) |

逐方法复核贯通输入、数据、编排、提示、阶段产物、反馈、求解、最终选择及页面展示。A 建立七种方法的基线，B 重构界面时复核既有方法，C 验收全部九种方法。组合矩阵只证明执行兼容，不能代替数学含义和展示检查。

接口由实际流程校正，后续可继续调整。谁改动接口，谁同步完成调用方、前端、配置、文档与测试，不把接线工作留给下一位。每阶段交接可运行提交、共用验收问题、逐方法复核结果、演示和简洁的已知问题说明。

新增数量保持为两种方法和两个求解器：B 接入 LLMOPT 与第一个新求解器，C 接入另一种方法与第二个新求解器。只固定 LLMOPT，其余由执行人选型。任务书用于分发和交接，具体规格、bug 和完成状态仍在 GitHub Issues 跟踪。
