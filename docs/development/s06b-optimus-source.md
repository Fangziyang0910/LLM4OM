## Observed entry, input and state

The complete algorithm entry is `main.py`'s `if __name__ == "__main__"` block, not an exported `run()` function. Its intended command is `python main.py --dir <public-problem-directory> --devmode 1 [--rag-mode problem_description|constraint_or_objective|problem_labels]`. This is an upstream interface description, **not a command run here**, and not a claim it runs without environment adaptation. CLI default `rag_mode=None`; `devmode=1` writes `run_dev`, otherwise the directory name contains date, model and Git hash plus `_RAG` even when retrieval is off. `MODEL="gpt-4o"` and `ERROR_CORRECTION=True` are hard-coded, not CLI options. Imports initialize clients and retrieval stores before entering the algorithm. [main.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/main.py), [utils.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/utils.py), [query_vector_db.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/rag/query_vector_db.py).

`create_state(parent_dir, run_dir)` requires `desc.txt` and `params.json`. Each parameter is keyed by symbol and must have `value`; generation later accesses `shape` and `definition`. The state retains parameter metadata after deleting `value`, while `run_dir/data.json` maps each symbol to its original scalar/list value. No source validation proves values match shapes or types. `get_labels()` unconditionally requires `labels.json`, even when RAG is off. Label retrieval uses `types` and `domains` lists. Main imports `get_params` but **does not call it**: provided parameter metadata/data are part of the input contract. [utils.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/utils.py), [main.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/main.py).

The evolving state contains `description`, `parameters`, then `objective`, `constraints`, and `variables`. `objective` and each main constraint have `description`, `formulation`, `code`, initially null where not yet generated. Variables map symbol to `{shape, type, definition}`. Shapes are lists of dimension symbols/integers; types feed `GRB.<TYPE>`. Auxiliary constraints initially have only `description="auxiliary constraint"` and `formulation`; code generation adds `code`. Objective formulation replaces its object with `{description, formulation}`, temporarily dropping `code`. No separate sets collection, explicit connection graph, background field, provenance ledger, or semantic verdict is created by this entry. These are actual output shapes, not five-element output. [constraint_model.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/constraint_model.py), [objective_model.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/objective_model.py).

**Constraint extraction EC really changes state.** `prompt_constraints_redundant` gets up to five parse attempts. `prompt_constraints_q` inserts the active question in `qs`, requesting an `x OUT OF 5` confidence. A parsed score above 3 keeps the constraint. A score of 3 or below calls `prompt_constraint_feedback` using hard-coded `gpt-4o`, even if the main model is different. Its JSON action is `yes|no|modify` with `updatedConstraint`. Missing confidence retries up to five times; exhaustion retains the list without an explicit failed-check status. The modify branch appends an uppercase-key object to a list otherwise containing strings; final wrapping can therefore produce a nested description object. Record this source behavior; normalizing it silently would change reference behavior. [constraint.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/constraint.py).

**Constraint formulation EC calls do not correct the model.** Only `qs[0:1]` is used. Its validator always returns `(False, constraints)` and `k=1`, so one confidence response is consumed per formulated clause, including auxiliaries, without updating state. The unit-consistency and variable-involvement questions, `logic_check`, `extract_score_constraint_model`, and `prompt_constraints_aux` exist but are not reached by main. New-variable name collisions raise; new shapes pass through `shape_string_to_list`; each original clause has one formulation attempt. Auxiliary clauses are accepted from that response rather than recursively formulated. [constraint_model.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/constraint_model.py).

Extraction is not a strict structured-response API. JSON/list parsers scan backwards for delimiters; the JSON fallback removes backslashes. Formulation extraction manually separates `$...$` strings before parsing the remainder. Code extraction accepts `=====` or fences and also removes occurrences of `python`. Keep raw replies and extracted bytes separately; do not silently replace these parsers during the first reference comparison. Invalid outputs can raise exceptions; most formulation/code loops have `k=1`, not a hidden repair policy. [utils.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/utils.py), [constraint_model.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/constraint_model.py), [target_code.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/target_code.py).

## Retrieval: invoked operations versus prompt effects

| Mode | Objective / constraint extraction | Constraint formulation | Objective formulation |
|---|---|---|---|
| None, CLI default | No retrieval query | No retrieval query | No retrieval query |
| `problem_description` | Problem-description vector search, top 5 | Problem-description search, top 5 | Problem-description search, top 10; result not inserted |
| `constraint_or_objective` | Problem-description vector search, top 5 | Each clause-description vector search, top 10 | Objective-vector search, top 10, but query is full `desc`; result not inserted |
| `problem_labels` | Label ranking, top 5 | Label ranking, top 5 | Label ranking, top 10; result not inserted |

Extraction and constraint formulation templates contain `{rag}`. **Objective formulation has no `{rag}` placeholder and does not pass it to `.format()`**, despite computing retrieval. Preserve even the unused query for call/cost fidelity. There is no code-stage retrieval. All three stores and `constraints.pkl` are nevertheless initialized at import, including in no-RAG mode. [objective.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/objective.py), [constraint.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/constraint.py), [constraint_model.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/constraint_model.py), [objective_model.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/objective_model.py).

The connected [query module](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/rag/query_vector_db.py) uses `OpenAIEmbeddings(model="text-embedding-3-large")` and LangChain Chroma. Problem-description search requests `top_k+1`, excludes exact identical text, then indexes exactly `top_k` results; too few can raise. Clause/objective searches request `top_k+20`, exclude identical queried text and rows matching `current_problem_name`, then use at most the available top-k. Constraint metadata `key` is a dataframe row index; objective lookup casts `key` to int. However, the vector-building notebook creates objective keys from `problem_name`, not constraint-row indices. This mismatch needs actual join/query evidence, not an assumed repair. Label ranking sorts by Jaccard of type-domain pairs, then sum of separate type/domain overlaps, then token-set description overlap; iteration starts from a set, so exact ties can vary. Callers of label ranking do not pass the current problem name. Exact-text exclusion is not a verified benchmark split barrier.

Retrieval text includes problem descriptions, objective descriptions, constraint descriptions and LaTeX formulations according to `RAGFormat`. It is modeling material, not merely a solver manual. The [extraction notebook](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/rag/extract_constraints_from_logs.ipynb) constructs this dataframe from latest GPT-4o runs under `test/`, selecting problems marked solved in `status.txt` and reading `state_6_code.json` plus labels. This is the observed construction recipe; the originating logs and record-by-record provenance were not inspected. The [vector notebook](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/rag/constraints_to_vector_db.ipynb) builds three collections from that dataframe. Do not rebuild them with a different embedding model and call that the same retrieval resource.

Actual fixed SQLite files contain 723 constraint embeddings, 217 objective embeddings and 217 problem-description embeddings; metadata keys are `key` and `chroma:document`. Their counts were read with SQLite `mode=ro&immutable=1`, without loading Chroma or making embedding calls. Static pickle scanning found the expected description/formulation/labels/problem-name keys; it did not unpickle or validate dataframe relationships. All retrieval bytes have manifest hashes. **The exact corpus's row origins, authorized reuse, split overlap and objective-key alignment remain unresolved.** Code MIT and the separate NLP4LP restriction must be recorded separately. An authorized frozen public corpus is a prerequisite to a RAG support claim. Replacing or filtering it is a documented resource/behavior difference; disabling retrieval to fit the SDK is not a faithful adaptation of a selected RAG mode. No-RAG is already a real upstream mode and may be tested under its own identity.

## Native execution, feedback and limits

`generate_code` assembles imports, `Model("OptimizationProblem")`, loading local `data.json`, parameter assignments, variable declarations, all constraint snippets, objective snippet, `model.optimize()`, and output handling. Scalar variables use `addVar`; indexed variables use `addVars` with parameter dimensions. No explicit lower bound is supplied. The generated tail accesses `model.objVal` before checking status; the nonoptimal branch attempts `f.write(model.status)` with an integer. Consequently, a solver termination without a usable objective can itself trigger source debugging. Only gurobipy generation is implemented; this does not establish native→HiGHS support. [generate_code.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/generate_code.py).

`execute_code` uses a local Python subprocess, captures stdout/stderr, and treats exit zero as success. Success writes `code_output.txt` with an “Optimal Revenue” prefix plus all stdout; the generated script also writes `output_solution.txt`. These text files are **not trusted API SolveResults**. `execute_and_debug(max_tries=3)` runs `code.py`, then on failures `code_1.py` and `code_2.py`; three failures generate `code_3.py` but never execute it. Each failure saves `error_<iteration>.txt` and uses `debug_template` with latest code and stderr, not accumulated error history. Success stops immediately. Exhaustion logs a message and returns no structured error or final filename; main does not save revised state. Persist all revisions and distinguish last executed from last generated. [execute_code.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/execute_code.py).

There is no shared token/LLM/solver budget, explicit temperature, output-token limit, solver TimeLimit, subprocess timeout, cancellation or dependency lock in this tree. Import/runtime dependencies observed: `openai`, `groq`, NumPy, pandas, `python-dotenv`, `langchain_chroma`, `langchain_openai`, Chroma and gurobipy; notebook building also imports LangChain `Document`. Versions are unspecified. `utils.get_response` sends one user message: model `llama3-70b-8192` selects Groq; all other model names select OpenAI. Main passes GPT-4o to its primary stages and debug calls; low-confidence extraction feedback independently selects GPT-4o. Keys/org in source are placeholders, not a usable configuration. `rag_utils` searches for `.git`, loads dotenv and creates a directory; `query_vector_db` has cwd-sensitive `sys.path` manipulation. These import effects must be replaced by explicit admitted resources, not copied into the host. [utils.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/utils.py), [rag_utils.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/rag/rag_utils.py), [query_vector_db.py](https://github.com/teshnizi/OptiMUS/blob/e182e9ef5841605c2a7e87467021fd83522b6484/rag/query_vector_db.py).

For resource planning, let E be constraints after redundancy, C be main plus auxiliary formulated clauses, R be extra malformed-answer attempts, F be low-confidence feedback calls, D be debug calls (0–3). In the normal parse-success EC path, chat calls are `5 + 2E + 2C + F + D`; add R for source retry loops. Solver/script attempts are at most 3, independent of whether the last generated repair exists. This is derived from the connected loops, not a fixed global budget. Embedding queries are additional resources in vector RAG modes; label mode needs no query embedding. Platform hard limits must bound the whole run and report a truncation/exhaustion difference if they stop upstream work.

## Implementation decisions: smallest complete adaptation

These are proposed changes, not observed implemented behavior. Baseline [methods.py](../../src/llm4om/methods.py) exposes `MethodContext(llm,data,budget,problem_sha256)` and one `ModelProposal`; [application.py](../../src/llm4om/application.py) requires candidate `001`, prepares it before one execution, validates CSV inputs and persists a factory with `entry_point=build_model`. [providers.py](../../src/llm4om/providers.py) accepts a role label but routes to one Provider/model and rejects embedding requests and sampling options. `validate_formulation` currently only accepts five elements despite the documented native-formulation direction. These are concrete incompatibilities, not reasons to alter upstream reasoning.

| Seam | Necessary minimal expansion | Scope boundary |
|---|---|---|
| Public input/data | Versioned public OptiMUS parameter metadata, symbol-to-value JSON and labels; explicit validated data bindings; preserve source description bytes | Admit JSON/file inputs in addition to CSV, or an explicitly reversible public conversion carrying the same metadata. Do not LLM-infer parameters as a hidden substitute for supplied `params.json`; no oracle-derived labels |
| MethodContext | Implement the already documented execution and public artifact/event access needed to persist states and execute intermediate script revisions | Execution returns public bounded stdout/stderr, exit/limit status and trusted solve refs; shared run deadline and counters; no evaluator or credential access |
| Gateway | Preserve each source prompt as a single user message; record primary/check/feedback/debug role and actual model; route external query embeddings through a budgeted admitted resource when vector RAG is selected | One configured general external chat model can serve all roles, explicitly recorded as a role-model change. A single-model run does not need a new expert orchestrator. New role routing is needed only to retain unequal source role models |
| Retrieval resources | Method-owned retrieval adapter over pinned, permission-checked corpus and index; mediated embeddings; record query, result IDs/order/scores and rendered retrieval hash | No core OptiMUS special case or replacement retrieval algorithm. Retain unused objective queries and existing exclusion/key behavior in strict reference mode |
| Candidate/Formulation | Accept declared `native_formulation` schema containing source state; persist stage snapshots, call refs, raw replies and source snippets | No fabricated five-element semantics or mandatory IR. Original formulation remains separate from later exported model views |
| Candidate/Code/Execution | Version a raw native script contract; save each full revision with parent and attempt refs; expose intermediate execution and final executed selection | Generic script representation, not `build_model` imposed on LLM output. Reuse valid final execution evidence instead of an extra silent solver call |

The method plugin keeps all source loops, checks, parsers, auxiliary-variable accumulation, retrieval choices, assembly and debug selection. Generic core changes reach capability/preflight profiles, input/formulation/code validation, Worker protocol, candidate persistence, shared resource ledger and final application reporting. Callers, public fixtures and contracts must be updated together when implementing these seams. Stage logging should cover **all** prompts, including currently unlogged objective/code calls, without changing their bytes. Opaque internal state snapshots suffice for this slice; full general checkpoint/resume, UI, new experts, alternate solvers, training and bulk benchmark execution are not prerequisites.

### Raw script execution with a separate trusted collector

Keep `code.py` and every repair byte-for-byte as original method outputs. Run the raw script only in an untrusted child within the admitted no-network, read-only-input container, with a bounded scratch directory for its original output files. Supply only admitted `data.json` and public assets. Keep Provider credentials out; never run the script on the host. Preserve source script stdout/stderr and exit status as the method's debug feedback. OS isolation, not a Python wrapper, enforces resource/process boundaries. [ADR-0005](../adr/0005-factory-collector-isolation.md).

For the observed main's simple `model.optimize()` workflow, a versioned execution harness can capture the native model immediately before optimize via the Gurobi SDK, export MPS plus variable order/names and source hash, then allow original optimize/output handling to proceed. The harness may load the unchanged script in its child namespace; it must not require an LLM rewrite to a factory. The export is an **untrusted proposed model**, never a SolveResult. Capture artifacts remain available on script failure, but failure still feeds source debugging. Require one supported model/solve for this profile; inability to capture, multiple models, non-linear/general constraints, unexpected optimize use, or missing maps produce explicit extraction/capability failure, not inferred success.

Pass validated export bytes across a size-bounded channel to a **fresh trusted collector process** with no shared Python modules, inherited child descriptors, or mutable child environment. Reuse S06-A native import/validation and a new SDK model to independently solve the exported admitted LP/MILP, then collect actual status, incumbent availability, objective, variable vector, bound/gap and resources. API results come only from this collector. Child stdout, `output_solution.txt`, child-side attributes and any alleged solver status are diagnostics. Collector-derived variable identity must validate the export ordering/names; child maps are not trusted measurements. Duplicate names or unstable symbol mapping must be explicit, not guessed. Export remains `native_exported_instance`, not proof of source/problem equivalence.

This adds a capture hook and, when trusted API results are requested, a separate solver call. Both are execution differences to measure and budget. Preserve the source raw exit-success stop condition separately from collector validity: collector-only failures cannot silently initiate new LLM repair calls. A failed source run can have a valid exported model; that does not make it the source-selected successful candidate. Do not select the final unexecuted repair after exhaustion. General callbacks/sifting or other absent paper modes would require a different capture contract; they are outside this fixed-main slice. Hook compatibility and isolation are proposals requiring runtime evidence, not verified capabilities.
