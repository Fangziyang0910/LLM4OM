# pzh 分支工作与验收记录

整理日期：2026-10-28。基线：v0.43.0，`ced6893fc7441925415fef451e398885ac6e5b76`。

本分支工作分为三部分：修复已经定位的程序问题；运行基础题并独立核对结果；记录复杂问题中的建模、解读与运行机制缺陷。第三部分的发现尚未全部修复，不能列入已完成修复。

本记录根据保存的差异、日志与验收结论整理，没有为更新文档重新调用模型或执行测试。原始运行数据、模型调用归档、私有设置、许可证、截图和本机环境不随本文提交。旧版人数域与JSON解析修复不属于当前分支；上游已有的13种方法、建模库和宿主功能也不计为本次新增实现。

## 已完成的bug修复

### 1. LLMOPT自我校正

原问题：缺少判断时默认通过，冲突判断可能只读取第一项；回到建模或代码步骤后，没有传递具体反思，容易重复原错误；达到重解上限后未清楚说明末次产物尚未通过；用户无法查看完整反思内容。

改动位于[`methods/llmopt/graph.py`](../src/llm4om/methods/llmopt/graph.py)：

- 要求五要素与代码各有明确且不冲突的True/False判断，兼容模板常见Markdown格式。
- 将实际反思和上一版产物传给被否定的步骤，代码重写还收到上一轮执行反馈。
- 保存原始反思为公开步骤，供页面与运行记录核对。
- 保留模型错回建模、代码错回代码的路线，以及最多12次重解；耗尽后明确报告未通过，保留实际结果。
- 实际代码执行失败时，不能因判断者声称通过而接受结果。

验证包含修复前复现、脚本化判断与反馈分支、真实CLI连续规划、Web整数生产、反思查看及条件调整后的新旧方案核对。历史脚本化检查日志记录过10项相关检查通过，另有执行失败保护1项通过；这些不计为真实模型调用，真实CLI/Web运行另行提供证据。

### 2. 原题与完整附件交接

原问题：上游F2C只根据五要素生成代码。数学表述若将参数写成省略号或“见表格”，下一次独立模型调用可能拿不到源数据，继而补造坐标、需求或默认数据。

本分支让建模、代码生成和自检读取原题及完整`context.data`附件，代码步骤同时读取五要素。要求保留实体ID、数值、单位及对应关系，禁止默认数据补缺；必要数据缺失或存在无法消解的矛盾时，可返回`MISSING_PROBLEM_DATA:`及具体原因，平台明确失败而不求解虚构模型。

验证覆盖原题数值、CSV文件名与内容、附件20000字符之后的关键记录、缺失数据拒绝，以及修正时原始数据和反馈同时保留。5项交接检查修复前失败、修复后通过。真实配送和CSV案例另行核对坐标、需求、原编号、容量及路线距离；缺失坐标案例明确停止且没有求解。

这改变了上游仅依据五要素写代码的输入机制。运行参数记录`code_context=problem_and_formulation`；方法适配差异维护在[建模方法](methods.md)。它不是对所有生成模型的数据保真作确定性保证，也不证明数学约束正确。

### 3. 面向提问者的方案解读

原问题：摘要只允许定性说明，容易重复目标、约束和模型结构，没有回答用户需要的具体安排；程序下标可能被误当成城市或产品编号。

改动位于[`followups.py`](../src/llm4om/followups.py)：摘要直接给出实际选址、产量、分配以及费用或收益，使用实际解值和原单位。实体名称依据执行代码与原数据追溯，不机械加一；无法确认时说明未确认。说明允许为空，避免模型教程、无用算式和未验证结论。表格数值继续来自实际求解结果。

真实模型重放将消防站旧代码的`y[1]`和`y[3]`正确解释为城市2、4，共2座；另用新Web运行核对。生产案例直接回答A生产3件、B生产2件、利润13。原保存结果和旧历史没有被回写。

### 4. 合法零值变量误拒绝

原问题：CSV生产题中，实际产量为0的产品被正确解释为“不生产”，但后台只允许引用非零展示子集，导致整段解读被拒绝。

现在变量总数不超过100时，向解读提供全部变量，包括0；超过100时仍限制提示长度，但真实性检查使用完整求解变量集合。虚构变量和重复引用继续拒绝。

6项接口检查覆盖混合零值、恰好100项、提示外真实零值、全零、虚构与重复引用。同题真实API重跑得到三种产品产量3、2、0及利润13，解读与页面均保留零产量决策。

### 范围与核对方式

先完成6题×3种方法（Direct、Feedback Repair、LLMOPT）×2种后端（HiGHS、CBC）的36项测试。数值与解读交付36/36，严格模型核对35/36，发现Feedback Repair的打印机连续域偏差。

随后按方法和引擎分开扩测：

- 方法固定Pyomo、HiGHS和同一DeepSeek预设，共13×6=78项，复用前轮18项、新增60项。
- 引擎固定同一份已核对的Direct模型代码，共8×6=48项，复用HiGHS的6项、新增42次实际尝试。每题在各引擎使用相同代码哈希，不重新生成模型。
- 没有做13种方法与8类引擎的全交叉，也没有把同一引擎的多个接口当成不同引擎。
- 方法运行通过真实Web服务API完成，代码在Docker Worker内构建与求解；这轮扩测没有额外进行全部页面的视觉验收。
- 提取实际变量域、目标、约束和上下界；整数题枚举有界整数可行域，连续题核对顶点与无界方向；返回解代回原约束并重算目标，数值容限为1e-5。

## 复杂问题中的bug与局限

以下是复杂案例中实际发现的问题，不是已完成修复，也不表示问题规模大就必然触发。数学模型错误、数值求解表现、方案解读错误和平台运行机制应分别判断。

### 1. 配送MTZ约束错误

生成模型同时采用“未分配客户的辅助载重变量固定为0”和对所有客户对施加的MTZ约束，放松条件与变量边界不配套。已用满足原题要求的完整配送方案作反例：访问链要求某辅助变量至少54，未访问客户对应的约束却要求该变量至多48，得到`54 <= u <= 48`的严格矛盾。

错误已进入五要素数学模型，代码继承它，自检仍判断通过。它会排除合法路线，不能靠延长求解时间解决。当前完成了公式代入核查，尚未修复生成与审查机制。

### 2. 多条路径排名与数值尺度

电网案例的返回路线遗漏损耗13的合法路径。已在同一模型中构造更优可行解并逐类代入约束核对，说明最终`optimal`状态不足以证明得到了用户要求的精确前8条路线。

该模型采用极大的字典序权重，后续路线改善在总目标中占比很小。数值尺度与相对容差可能影响精确排名，但原记录缺少足够信息，尚未确认具体停止判据；不将其直接定性为某求解器通用bug。

### 3. 重复线路与业务口径

同端点的重复线路被字典覆盖，但邻接求和仍重复，导致对应边意外无法选中。并行物理线路应有独立标识；若原数据本身矛盾，需要澄清，不能静默选择。

电网案例还存在相加损耗与逐段损耗口径未澄清、内部加权目标误标为百分比的问题。配送CSV案例中，总里程正确但解读给出的分车里程错误。这些说明复杂结果的业务语义核对仍不完善。

### 4. 超时与继续执行机制不完善

复杂方法可能产生较多模型调用、候选构建和求解，容易受到模型请求、单次求解或整体运行时限约束。三种超时不能混为一个状态，也不能只靠统一增加时长处理。

本次观察与未完成内容：

- 尚未完成网页上为已超时任务追加时长、保留已有进度继续执行的完整交互与验收。
- 尚未完成继续执行与新建运行之间的明确关系，以及追加预算、已有调用和求解消耗的连续记账验证；不能把重新提交整题称为原地继续。
- 需要分别展示业务运行是否失败、最后一次求解是否有可用结果、方案解读是否完成，避免只看到一个超时提示而无法判断已有产物能否使用。
- AutoFormulation运行期间一次状态查询超过15秒，批测之后仍完成。这证明查询超时不能直接等同于业务运行失败；目前未据此确认根因。
- 本机每日额度调整只是测试环境配置，不是实现了新的超时、加时或恢复功能。

上述内容记录为复杂问题使用中的平台机制不足，没有在本分支新增加时或继续执行功能，也未对所有已有恢复能力作否定性结论。
