从运行页的失败阶段和完整错误开始定位。下面按连接、模型请求、求解环境、验证和恢复列出实际检查入口。

## 页面与服务连接

| 现象 | 检查与操作 |
|---|---|
| 本机打不开页面 | `docker compose ps`查看状态；`docker compose logs -f app`查看启动信息 |
| 其他设备打不开 | 检查服务器IP、端口映射、防火墙与安全组 |
| HTTPS证书问题 | 核对域名解析、80/443端口，查看 `docker compose logs -f https` |
| 流式进度中断 | 刷新运行链接重新连接；检查代理的实时流配置与服务日志 |

Python启动时查看终端打印的监听地址和工作区；Compose端口由 `LLM4OM_PORT` 决定。

## 模型预设与请求

| 错误 | 处理位置 |
|---|---|
| 401 | 核对密钥与服务商 |
| 404 | 核对接口地址、协议和模型ID |
| 结构化输出或工具选择错误 | 查看服务的工具支持、所选方法及高级参数 |
| DeepSeek运行TriVAL失败 | 在运行预设填 `{"thinking":{"type":"disabled"}}` |
| 额度提示 | 在预设窗口查看当天用量，选择可用预设或等待下一日 |

预设保存失败保留已输入内容。按[模型配置](../model-presets/)重新添加正确配置，再用小案例确认调用。

## 求解环境与代码执行

找不到Worker镜像：Compose运行 `docker compose up -d --build`；Python方式运行 `uv run llm4om build-worker`。

Docker连接错误：检查Docker服务、socket权限与 `DOCKER_SOCKET` 路径。后端加载或许可错误：打开完整反馈，按[后端指南](../backends/)核对原生依赖和挂载文件。

代码错误显示具体异常与执行步骤。可定位文件名、数据字段、索引、模型返回对象或库API，再从原题运行所需修复流程。

## 方法验证与求解结果

TriVAL保存语义、公式和代码验证状态；SAC-Opt保存逐约束语义比较；Feedback Repair保存接受或修复理由。运行页的失败信息会指向具体阶段，过程页保留产物和执行结果。

先打开该阶段，阅读反馈，再对照对应版本的模型和代码。各方法文章提供停止条件、返回路径与参数，可以直接定位运行走到哪一步。

## 不可行与原生状态

有IIS或MUS证据时，使用[冲突分析](../conflicts/)找到业务规则并进入调整。非线性路径可查看初值、边界和原生反馈，再运行其他场景。

时限、调用次数和每日额度在运行信息中有对应记录。调整部署额度见[配置](../configuration/)，选择模型类型见[求解器](../solvers/)。

## 恢复与问题记录

刷新对话可连接活动运行，已完成方案从卡片或历史打开。停止后可重试原消息；批量场景重试复用已保存项并继续剩余计算。

记录问题时整理以下信息：运行链接、方法、库、后端、预设显示配置、失败阶段、完整错误和相关题面。这样可以把问题直接对应到具体输入与执行路径。部署日志与工作区备份见[团队维护](../configuration/)。
