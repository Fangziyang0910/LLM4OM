一次运行由问题、建模方法、大模型和求解环境共同决定。理解它们的分工，有助于选择配置和阅读结果。

## 从问题到方案

```text
自然语言问题 + 数据
        ↓
建模方法组织大模型调用
        ↓
数学模型 + Python 求解代码
        ↓
沙箱执行代码，求解后端计算
        ↓
状态、目标值、变量取值与过程记录
```

## 四个容易混淆的选择

| 名称 | 它决定什么 | 例子 |
|---|---|---|
| 建模方法 | 怎样生成、检查和修正模型 | Direct、TriVAL、BIND |
| 预设模型 | 哪个大模型提供推理与代码生成 | 你配置的模型服务与模型 ID |
| 建模库 | 用什么 Python 接口表达数学模型 | Pyomo、CPMpy、CVXPY |
| 求解后端 | 哪个引擎实际计算解 | HiGHS、CP-SAT、Gurobi、Ipopt |

更换大模型不会直接更换求解器。更换建模库也不自动扩大某个方法的问题范围。详细选择见[方法指南](../methods/)和[求解器指南](../solvers/)。

## 一次运行保存什么

每次运行固定保存当时的问题、附件、配置、步骤、数学模型、代码和实际结果。后续调整生成独立运行，便于核对原方案与新方案。预设后来被删除或服务器配置改变，不会改写已有运行记录。

## 怎样理解状态

- `optimal`：当前模型已有最优性结论。
- `feasible`：已有可行解，可能没有最优性证明。
- `locally_optimal`：局部求解得到的结论，常见于非线性优化。
- `infeasible`：当前模型不可行；有证据时可进一步查看冲突。
- 执行失败：代码、依赖、接口或运行限制导致流程没有完成。

求解状态与模型是否准确表达业务要求是两个判断。模型验证失败时，即使求解器返回最优，也应先阅读失败阶段和反馈。
