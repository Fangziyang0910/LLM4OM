Modeling methods/OptiTree

OptiTree

Match a problem type in a tree, retrieve guidance and generate code.

On this page

OptiTree searches a hierarchy of problem types before generating code. It makes “recognize the structure, then borrow a relevant modeling pattern” an explicit part of the workflow.

What the type tree provides#

Transportation, assignment and staffing descriptions can share variable and constraint structures. The tree provides reasoning templates, not complete answers. Costs, indices, capacities and special rules must still come from the current problem.

Matching starts at the Mixed Integer Programming root and selects only among the current node's children. The deepest matched node's full entry becomes context for generation. The process retains the matching path and retrieved entry.

Workflow and retrieval example#

FOLLOW THE EXAMPLE
1. Recognize structure

For warehouse-to-store transport, recognize quantities, supply and demand. The actual matching path depends on the bundled tree and LLM decisions.

Decisions: shipment quantities from warehouses to stores.
Inputs: unit costs, warehouse supply, store demand.
2. Use the template

A template can suggest indexed x[i,j], but the current wording determines whether supply and demand require equality or inequality.

x[i,j] ≥ 0
Warehouse: sum_j x[i,j] ≤ supply[i]
Store: sum_i x[i,j] ≥ demand[j], if required by the problem
3. Generate and execute

Use the retrieved entry together with current data. Template example values must not replace user data.

Check warehouse/store indices and cost-matrix orientation.
Special business rules still need explicit constraints.
4. Handle no match

Stop at the current node if no valid deeper type exists. Do not invent a classification. Inspection repairs execution failures.

Unknown type / missing judgment / repeated path → stop descent
At most 4 code inspections.

Worked example: illustrative inputs and intermediate artifacts.

Why a broader match can be useful#

A specific but wrong type can impose the wrong structure. Treating divisible transport as one-to-one assignment can invent a restriction against split shipments. A broader match supplies general guidance while leaving details to the problem.

Read the path, retrieved entry and final formulation together. The process shows the path and entry; the final model shows selected variables and constraints.

Scope and related methods#

The current workflow targets LP/MILP, uses temperature 0 and permits four code inspections. Use it to study the effect of type retrieval. For component construction see OptiMUS; for searching multiple complete candidates see AutoFormulation.

Source and platform adaptation#

The platform ports the pinned OptiTree implementation, including its type tree and templates. It retains classification, reasoning and inspection prompts, supplies native-library contracts, and stops safely on unknown types, missing judgments or repeated matching paths.

Current parameters#

Parameters come from the deployed method preset. They are saved with each run and cannot be changed per run in the UI, CLI or Python API.

temperature0
max_inspections4
