Feedback Repair

求解后对照原题复核，并按具体问题修正。

本页内容
执行流程怎样使用怎样阅读失败与不可行实现来源当前参数

Feedback Repair 在 Direct 的生成基础上增加求解后复核。它对照原问题检查目标、变量域、约束与数据绑定，并根据具体错误修正模型或代码。

执行流程#

生成 → 求解 → 对照原题复核 → 结束
  ↑        格式、执行或建模问题 ↓
  └──────── 按反馈修正 ────────┘

即使求解器报告最优，复核仍检查数学模型是否符合题意。可用的冲突诊断也会参与复核。没有修正时，方法本身使用两次大模型调用和一次求解；后续方案解读另计。

怎样使用#

在运行设置选择 Feedback Repair。它适合希望在得到数值后再进行一次题意检查的工作流。仍需准备清楚的要求与数据，并选择兼容的建模库和后端。

格式、执行和建模修正共用最多三次修正额度。超时、仅有可行解或可满足性问题没有目标值，不会单独成为改写模型的理由。

怎样阅读失败与不可行#

正确的不可行或无界模型可以正常结束，不会为了有解而放宽要求。复核未解决或回复无法解析时，保留已完成产物并说明失败。后续生成缺少格式时，最后一次实际求解的模型与结果仍可追溯。

实现来源#

这是本项目维护的方法。复核是一层额外检查，不是正确性证明；它没有引入 SAC-Opt 的语义锚点或 OptiMind 的专项提示库。

当前参数#

参数来自部署时的方法预设，随每次运行记录保存。页面、命令行和 Python 接口均不提供单次运行的参数修改。
